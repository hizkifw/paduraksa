# Paduraksa - Design & Implementation Plan

> **Paduraksa**: the gate into the inner sanctum, flanked by guardian figures meant to keep evil out.
>
> Open-source, homelab-grade reverse proxy and lightweight WAF on **Kestrel + YARP**. You deploy it once and manage it from the dashboard, the REST API, MCP or the CLI. It covers what nginx-proxy-manager does, adds versioned config, an audit trail, real multi-user support and a hot path designed for speed from day one.

Status: **v0.17**: M0-M4 done, M5 in progress (see §18) · Target runtime: **.NET 10 (LTS)** · Single node, single process.

---

## 0. Goals / non-goals

**Goals**
1. **Performance.** The request hot path never touches the DB, takes no locks and allocates nothing in Paduraksa code that can be avoided. Config changes are published as immutable snapshots swapped atomically.
2. **UX.** A first-run wizard gets you from zero to a wildcard cert and your first host in under 5 minutes. Every change is previewed as a diff, versioned and reversible.
3. **Manage everything without a shell.** Dashboard, REST API, MCP and CLI are thin skins over **one** application layer, so features never drift between surfaces.
4. **Security by construction.** Typed IDs everywhere, DTO/entity separation, and a key-material trust boundary enforced by the compiler.
5. **Batteries included, kept small.** ACME (HTTP-01/DNS-01), uploaded/self-signed/local-CA certs, WAF primitives, error pages, robots.txt, metrics.

**Non-goals (for now)**
- OWASP CRS or ModSecurity-style deep inspection. The WAF is deliberately simple and fast.
- Clustering/HA. It's a single node, though state is easy to back up and restore.
- L4 (TCP/UDP) streams. These come later, after HTTP is solid (see §14).
- Native AOT. Blazor Server, EF Core and YARP rule it out today. We use ReadyToRun + Dynamic PGO instead.

## 2. Development rules → how they're enforced

| Rule | Mechanism |
|---|---|
| **Typed IDs all the way to EF** | `[TypedId]` source generator; EF conventions map every typed ID automatically; BannedApiAnalyzer bans `Guid.NewGuid()` repo-wide; an arch test fails if any `Contracts`/entity property named `*Id` is `Guid`/`string`/`long`. |
| **DTOs decoupled from entities** | `Admin`/`Dashboard` can't reference `Data` (project graph + arch test). Mapping is explicit (hand-written or Mapperly source-gen), never reflection auto-mapping. DTOs are `sealed record`s. Entities never get serialized (an arch test checks that no `Data` type appears in a JSON context). |
| **Trust boundary for key material** | `BannedSymbols.KeyMaterial.txt` bans private-key export/load APIs, `AesGcm` and `HMAC*` in **every project except `Paduraksa.Vault`** (already wired up in `Directory.Build.props`). The vault exposes *capabilities* (sign, decrypt-and-use, select-cert), never bytes. Its types are `internal`, and only the Server composition root registers it. |
| Warnings are errors, nullable on | `Directory.Build.props` |
| **Prose spelling** | British, like the rest of the repo: *enrol*, *enrolled*, *enrolment*; *normalised*, *behaviour*. Identifiers and wire names are left as they are (`BeginEnrollmentAsync`, `me/totp/enrollment`), so code and URLs don't change. |
| **No secret in a log - one decided exception** | The setup token is logged, in a boxed banner at Warning (PLAN §12.1). Owner decision: it is single-use, worthless once an Owner exists (and deleted then), and anyone who can read the log already has the host's shell, and with it the token file. Everything else (passwords, cookies, API tokens, keys, DNS credentials, EAB keys) never reaches a log, a problem or the audit trail. |
| Central package versions | `Directory.Packages.props` |

## 3. Process & hosting model

Fleet mode (§16.1, after v0.1) splits this into a control plane and a data plane; the single-node model below stays the default.

One process, **two web apps** (the public app on the generic host with an explicit pipeline since M1, §7.1; the admin `WebApplication`) plus a non-web **core host**, one shared set of core singletons:

```
                    ┌──────────────────────── paduraksa process ────────────────────────┐
 :80  (H1)  ──────► │ PUBLIC APP                                                         │
 :443 (H1/H2/H3) ─► │  conn middleware ─► TLS(SNI) ─► Gate ─► host policies ─► YARP ─────┼─► upstreams
                    │          ▲                 ▲                                       │
                    │          └── SnapshotStore (volatile ref, immutable RuntimeSnapshot)│
                    │                            ▲ publish                               │
 :9443 (H1/H2) ───► │ ADMIN APP  Dashboard · /api/v1 · /mcp · /metrics ─► Application ──┤
                    │                                                     │   │          │
                    │                                   Data(SQLite) ◄────┘   └─► Vault  │
                    └────────────────────────────────────────────────────────────────────┘
```

Implemented in M0 (`src/Paduraksa.Server/Hosting`):
- **Shared singletons:** `SharedServices` accepts only ready-made instances and registers the *same* objects into every container. It disposes them exactly once, after all hosts have stopped. `PaduraksaOptions` itself is the shared instance, and `IOptions`/`IOptionsMonitor`/`IOptionsSnapshot`/`IOptionsFactory` all resolve to it (named options throw).
- **Core host:** a non-web host owns every once-per-process `IHostedService` (ACME scheduler, metric sampler, ...). It starts first, so a snapshot exists before any port opens, and stops last. Web apps must not register once-per-process background services.
- **Startup:** if any host fails to start, the others are stopped and the process exits 2. A stop, a signal or a cancelled start token that arrives during startup aborts the start instead: whatever had started is stopped again and the process exits 0. A requested abort is logged at Information, never as an error.
- **Exit codes:** 0 = stopped on request, including during startup. 1 = a host stopped on its own, a host failed to stop, or disposal failed after an otherwise clean run. 2 = startup failed (including no config to serve, §6.4) or the process couldn't be built. 3 = invalid config: failed validation or an unparsable appsettings file. Validation failures print a header plus one line per failure on stderr; any other failure to build or dispose the process prints a single line (`PADURAKSA_DEBUG=1` adds the stack trace).
- **Data directory:** a relative `Paduraksa:DataDirectory` resolves against the content root (where appsettings live, by default the app's base directory), never the working directory. A leading `~` is rejected because nothing expands it. It holds the config database `paduraksa.db` and `last-good.json` (§6.4), and is created at startup if missing.
- **Shutdown:** `/readyz` switches to 503, public drains, then admin stops, then core stops, then shared singletons are disposed. One `ShutdownTimeout` (30 s) is shared by all three, so compose files need `stop_grace_period: 35s`.
- **Signals:** handled only in `PaduraksaHost.RunAsync`. A second signal hard-kills.
- **Listener pinning:** the web apps get a last config source that blanks `urls`/`http_ports`/`https_ports` and sets `preferHostingUrls=false`. Env vars and appsettings can't rebind listeners behind our back.

Public listeners as integrated in M1 (`Hosting/PublicApp.cs`, `PublicListenerSetup`), all on dual-mode `[::]` (`0.0.0.0` without IPv6):
- **HTTP** (`Listen:Http`/tcp, H1) and **HTTPS** (`Listen:Https`/tcp, H1/H2): the stage-A `ClientInfo` connection middleware (PROXY protocol first when enabled on that listener), then on HTTPS the per-SNI TLS callback reading the live snapshot's certificate table (§7.2 B).
- **HTTP/3** (`Listen:Https`/udp): added when `Listen:Http3` is on and libmsquic is present. Its TLS callback selects the certificate and attaches `ClientInfo` (§7.2 A). Without libmsquic it is off, with one Information log at startup; `Alt-Svc` is then never sent.
- **One `TlsHandshakeSelector`** per process (shared singleton, its rejection counters are process state). The same options also derive the compiler's `SnapshotCompilerOptions` (public port, whether H3 is advertised, the certificate resolver), so listeners and snapshots can't disagree.
- **Certificates:** the process's `IServerCertificateSource` is the vault's, then (only when `Paduraksa:Development:PlaceholderCertificate` is on) `PlaceholderCertificates` for the IDs the vault does not know (§9.2). The placeholder is the in-memory self-signed certificate under a well-known, stable `PlaceholderCertificates.Id`; it is also a built-in inventory entry and the inventory's fallback default, so with it on, a config that names no default certificate still answers HTTPS for every host, and a stored document that names the ID keeps compiling across restarts. The option defaults to **on in a Debug build and off in a release build**, where a name no vault certificate covers is rejected at the handshake (the tests and the benchmark runner switch it on explicitly, and a release process with it on warns at startup). The admin listener's own certificate is issued from the local CA and kept current (see **As built (M4): the admin certificate** below); the placeholder is only its last-resort fallback. The vault starts first in the core host: **a wrong, missing or unsafe master key stops the process** (exit 2, Critical log entry), because running without the vault would only move the failure to the first certificate that needed a key.

Options under `Paduraksa:Listen` (validated at startup, invalid → exit 3):

| Key | Default | Meaning |
|---|---|---|
| `Http`, `Https`, `Admin`, `AdminBind` | 80, 443, 9443, `0.0.0.0` | As before. TCP and UDP share `Https`. |
| `AdminInternal` | `true` | The admin app's internal admin listener for an admin host (PLAN §3.1): a Unix socket at `<data dir>/run/admin.sock` (0600, in a 0700 directory), or `127.0.0.1:<ephemeral>` where one can't be bound. On by default and independent of the config, so creating an admin host needs no restart; off, a config with an admin host is refused. No TLS: it is process-local plumbing. |
| `PublicHttpsPort` | 443 | The HTTPS port clients reach: advertised in `Alt-Svc` and used by the HTTP→HTTPS redirect. Set it only behind a port mapping. |
| `Http3` | `true` | Serve H3. Off, with an Information log, without libmsquic. Needs a fixed `Https` port (0 is rejected with H3 on). |
| `HttpProxyProtocol`, `HttpsProxyProtocol` | `Enabled: false`, `TrustedSources: []`, `HeaderTimeout: 00:00:03` | PROXY protocol v1/v2 on that TCP listener (HTTPS: read before TLS). Enabling it makes the header mandatory and requires at least one trusted source (address or CIDR); the timeout is at most 1 min. QUIC has no PROXY protocol. |

Why two apps and not one app with port filters:
- Admin endpoints **can't be routed** on public ports, because the public pipeline doesn't contain them. No reliance on `RequireHost` or port checks.
- Each pipeline gets its own middleware, auth and Kestrel limits (for example, admin allows large YAML uploads while public uses per-host limits).
- Shared singletons (`SnapshotStore`, `MetricsRegistry`, `Vault`, `IAcmeChallengeStore`, `HealthState`) are built once and registered **as instances** in both containers.

Ports (configurable, env-overridable):

| Purpose | Default | Notes |
|---|---|---|
| Public HTTP | 80/tcp | ACME HTTP-01, redirects, plain-HTTP hosts |
| Public HTTPS | 443/tcp + **443/udp** | H1/H2 over TCP, H3 over QUIC. Docs must stress mapping the UDP port. The container listens on 80/443 *directly* (no in-container remapping, see §16) so the advertised `Alt-Svc` port is correct; `Listen:PublicHttpsPort` overrides it behind a mapping. |
| Admin | 9443/tcp | HTTPS with an internal-CA cert. The wizard offers the root CA for download. Bind address and allowed CIDRs are configurable. Never plain HTTP on the LAN. |
| Admin fallback | loopback only, plain HTTP (opt-in, e.g. `127.0.0.1:9080`) | For headless/SSH-tunnel setups. Refuses to bind to anything but loopback. |

**As built (M4): the admin certificate.** The admin listener's certificate is the process's own leaf, issued by the vault's local CA and kept current, so the wizard's "trust this root once" makes the admin UI trusted in the owner's browsers.
- **Root.** The core host (after the vault and the config store) ensures the local CA root exists through the quiet `CertificateOperations.EnsureAdminRootAsync` path (as the system, registering without republishing), so there is never a second one: the inventory's active root while the vault still holds its key, else the root the vault already holds - adopted, never re-created, labelled `Recovered from the vault` so it does not matter which writer got there first - else a new one (§9.2). A row left behind by a lost `vault.db` (active, but the vault holds no key for it) is retired as `failed` and replaced, so the admin certificate comes back on its own. `CertificateOperations.EnsureLocalCaAsync` stays the ordinary, republishing entry for the other surfaces.
- **Leaf.** It is the leaf under the stable `AdminCertificate.Id` (`Paduraksa.Application.Certificates.AdminCertificate`, a well-known UUID like the placeholder's) with source `local_ca` and the label `Admin (internal CA)`. A new `CertificateSource` value was considered and rejected: the `Certificates` table's `CHECK` constraint would need a table-rebuilding migration for no behavioural gain, and the stable ID plus the label already identify it. Its names are `Paduraksa:Admin:CertificateNames` (validated at startup: DNS names and IP addresses, no wildcards, no IPv6 zone ids, at most 95 so the total stays inside the vault's 100) plus `localhost`, `127.0.0.1`, `::1`, the machine's host name and a specific `Paduraksa:Listen:AdminBind` address. It is re-issued only when that name set changes or when a third or less of its lifetime is left (`AdminCertificatePolicy.ShouldReissue`, pure arithmetic over the stored facts), always under the same ID. Deleting it (`certificate.managed`) and re-issuing it by hand (`certificate.managed`) are both refused: the process owns its lifecycle, because a hand re-issue would swap the vault's key while the listener kept the old context for up to a day.
- **Reserved.** The admin leaf is the admin port's alone: `CertificateInventoryLoader` leaves `AdminCertificate.Id` out of every inventory it builds for the compiler, so Auto never picks it and its validity boundaries never trigger a republish; `ConfigValidator` refuses it as a Specific binding (`host.certificate.unusable`) and as the default certificate (`settings.defaultCertificate.unusable`), each saying it is reserved for the admin listener. That is why nothing in the document can bind it - not "it happens not to be named today".
- **Serving.** The listener gets a per-handshake `ServerOptionsSelectionCallback` (`AdminCertificateService.CreateTlsOptions`) that returns the vault's `SslStreamCertificateContext` wrapped in `SslServerAuthenticationOptions`, exactly the sanctioned egress the public listener uses; a renewal swaps the options and the next handshake gets the new certificate, with no restart. The private key never leaves the vault (the key-material ban list holds, and `PaduraksaKeyMaterialBoundary` is not set on Server).
- **Startup and renewal.** `AdminCertificateService` (a shared singleton, `BackgroundService`) is a hosted service of the core host only. Its `StartAsync` ensures the certificate **before the web apps bind**, so the admin port serves the local-CA certificate from its first request, and a daily loop re-runs the check. That wait is bounded by `Paduraksa:Admin:CertificateStartupTimeout` (10 s, 1 s to 5 min): the public proxy on 443 binds at most that long after the core host, and a slow vault continues the work in the background - **the run serves what the vault holds before it starts the inventory step**, so the admin port shows the vault's certificate even while that step is slow - under a token the service owns: `StopAsync` cancels it and waits for it, so the run never outlives the hosts that own the vault and the config store. Registering the certificate never republishes the live config (`CertificateService.RegisterQuietlyAsync`): nothing can bind the process's own certificate, so the step must not wait for the public app's YARP, and no snapshot generation moves. The leaf's creation and every re-issue are still audited and visible in the certificate inventory. Issuance and re-issue are skipped entirely while the config store refuses changes (a degraded start), as in `CertificateRecoveryStartup`: a due re-issue there would replace the vault's key and then fail to record it, every day.
- **Fallback.** Whatever the inventory step does - it fails, or the store is degraded - the run still serves the certificate the vault holds, and only falls back to the placeholder when the vault has nothing servable (none, or outside its validity period; `AdminCertificatePolicy.IsServable`). A failure must not discard a valid certificate: the admin sends HSTS for non-loopback names, so a browser that trusted the root has pinned the name and the self-signed placeholder would be a hard error with no click-through. Nor may a rollback: a failed creation for the admin ID keeps the vault's key (the ID is fixed, so the pair it holds may be the only servable one) and only its row is rolled back, and the next run adopts whatever the vault has. Failures are logged at Error, with the exception. There is deliberately no Debug/Release switch here: the placeholder is the last resort, not a mode.
- **A lost vault.** If `vault.db` goes while the config database keeps its rows, the rows name a root and a leaf the vault no longer holds. The run notices (it asks `ICertificateCatalog` about the active root's ID and about the admin ID), retires the stale root as `failed`, makes a new root and issues a new leaf under the same ID - no operator step, which matters because deleting the root, deleting the admin certificate and re-issuing it by hand are all refused.
- **Root CA download.** `GET /api/v1/ca/root.pem` (PEM, `application/x-pem-file`), `GET /api/v1/ca/root.crt` (DER, `application/x-x509-ca-cert`, the type Android and iOS offer to install) and `GET /api/v1/ca` (fingerprint, subject, validity as JSON; DTO `CaRootCertificate` in its own file, a member of the API's `AdminJsonContext`, written through `EndpointSupport.Json`). Each also answers `HEAD`. They are mapped with the rest of the resource API (`Api/CaEndpoint`, from `MapPaduraksaAdminApi`), so they get its problem details, its OpenAPI description and its JSON contract; all three are `.AllowAnonymousAdmin()`, and the prefix is one of the setup gate's allowed ones by default (`AdminPipelineHooks.SetupAllowedPathPrefixes`), so the wizard can offer the root before an Owner exists. They serve the **public** root only, from the in-memory `CaRootSource` the admin certificate service publishes on every run (never a key, never any other certificate, and no vault read per anonymous hit); the DER is decoded from the stored PEM, never loaded into an `X509Certificate2` just to re-encode it. With no local CA yet they answer 404 as the standard `ApiProblem` with code `ca.notFound`.
- **Startup log.** When setup is incomplete, the first successful ensure logs the admin URLs (one per concrete name) and the root's SHA-256 fingerprint at Information, next to the setup-token Warning, so a `docker logs` reader can verify the certificate they are asked to trust. Never key material.
- **Not built:** nothing renews the local CA root. It is valid ten years and the vault caps a leaf at the root's remaining validity, so in the root's last 90 days each re-issued leaf gets shorter, down to the root's expiry, after which the admin port falls back to the placeholder and the root download still serves the (expired) root. Rotating the root is deferred (§9.1, where the local CA root is described).
- **Docker.** `Environment.MachineName` is the container ID in Docker, and a recreated container gets a new one, so the name set changes and the certificate is re-issued on the next start. That is harmless (the ID is stable, the root unchanged) but it does mean a fresh serial after every `docker compose up --force-recreate`; `AdminCertificateNames.Compose` adds it as one name among the loopback ones, and set `Paduraksa:Admin:CertificateNames` for a stable name to reach the admin UI by.

### 3.1 Exposing the admin through the proxy (opt-in)

Some people want `proxy.example.com` to be the admin UI, with the wildcard cert, SSO and WAF in front of it. Because the admin is a separate `WebApplication`, the public app reaches it like any other upstream:

- The admin app gets an extra **internal admin listener**: a Unix domain socket in `data/run/admin.sock` (0600), or `127.0.0.1:<ephemeral>` where UDS isn't available. The public app's YARP cluster `__admin` points at it (UDS via `SocketsHttpHandler.ConnectCallback`). WebSockets for the Blazor circuit pass through YARP unchanged.
- The admin app trusts `X-Forwarded-*` **only** on that internal admin listener, and the public side always overwrites (never appends to) those headers before forwarding.
- Cookies: `__Host-` prefixed, which browsers only accept with `Secure`, `Path=/` and no `Domain`, plus `SameSite=Strict`. They are bound to the host *name*, not the port: a browser sends `__Host-paduraksa-session` to every service on that name, so `https://proxy.example.com` (the proxied admin) and a proxied host or `https://proxy.example.com:9443` on the same name share it, while a different name or `https://lan-ip:9443` is independent. **The public proxy therefore removes that one cookie from every forwarded request** (a request transform: one ordinal search of the `Cookie` values when it is absent, a rebuilt header without it when present, every other cookie untouched), so an upstream never receives a live admin session. Antiforgery works unchanged because everything stays same-origin.
- **Proxying a host to the admin port makes every client look like loopback.** Whoever forwards a public name to `127.0.0.1:9443` (a proxy on this machine, or this one) hides each client's address behind the proxy's: all of them share one throttle bucket, and a source allowlist that lists loopback lets the whole internet in. Don't do that with the main admin port; the **internal admin listener** above is the supported way, and it carries the forwarded address under the authenticated hop rule below. Leave loopback out of `AdminAllowedSources` unless you mean it.
- The admin host is a normal `Host` (`Kind = Admin`): forced HTTPS, its own WAF/rate-limit/auth policy. It can't be deleted while it's the only way in (lock-out guard).

**As built (M4): the internal listener and the admin host.**
- **Listener.** `Paduraksa:Listen:AdminInternal` (default on, not reloadable) gives the admin app one extra **internal admin listener**, always present so an admin host can be added without a restart. It is a Unix domain socket at `<data dir>/run/admin.sock`: the constructor creates `run` with `Directory.CreateDirectory(run, 0700)` and sets that mode again if the directory exists, refuses a `run` that is a symlink or (where Linux exposes the owner) not owned by the process uid, connects to the real socket path to tell a live second instance (startup fails, Critical) from a stale file (deleted), and probes Unix-socket support on a temporary sibling name only. Where the probe fails (a platform without Unix sockets, a path too long for `sockaddr_un`), it uses `127.0.0.1:<ephemeral>` and logs a Warning with the reason; the port is recorded at `ApplicationStarted`, and the proxy's connect callback waits up to 5 s for it, so the fallback works although the public app starts alongside the admin app. The socket is `chmod`ed to 0600 from `ApplicationStarted`; its identity is recorded then and `Dispose` removes it only while it is still this process's. There is no TLS on it and it speaks HTTP/1.1 (the proxy's upstream connection is HTTP/1.1, and WebSocket upgrades are): plaintext stays inside the process boundary (or the loopback socket). The listener is marked on its `ListenOptions` by a connection middleware; nothing infers it from a port. `/mcp`, `/metrics` and the dashboard (later milestones) use the same listener. It is not listed by `GetListenAddresses`, which reports client endpoints only.
- **Public route.** An enabled admin host compiles to one implicit prefix route (`/`, whose `CompiledRoute.Id` is empty and whose `CompiledRoute.Admin` is true) against a single YARP cluster `__admin`. The cluster's one destination is symbolic (`http://admin.internal/`); `PaduraksaForwarderHttpClientFactory` gives that cluster a `SocketsHttpHandler.ConnectCallback` that ignores the destination and connects to the internal admin listener (`AdminInternalListener.ConnectAsync`), and pins its outgoing request to HTTP/1.1 (`VersionExact`). WebSockets are ordinary HTTP upgrades to YARP and pass through unchanged (a test drives a real `101` through the public listener and the admin pipeline). A config with an admin host while `AdminInternal` is off is a compile error; the compiler also refuses a second admin host, routes/redirect/respond on it, or `Https = false`. YARP's config is still a pure function of content: the symbolic address never depends on the chosen port.
- **Forwarded headers, with an authenticated hop.** The existing `ForwardedHeadersTransform` overwrites `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto` and `X-Forwarded-Host` (and removes `Forwarded`, `X-Forwarded-Prefix`/`-Port` and untrusted `cf-*`) on every proxied request, the admin route included. A separate transform removes any client-sent `X-Paduraksa-Internal` from every request and adds this process's 32-byte random hop secret only on the admin route; no upstream ever sees it. `AdminForwardedHeadersMiddleware` trusts the three headers **only** on a connection marked as the internal admin listener (the connection middleware on its `ListenOptions`, not a peer address or port) **and** only when `X-Paduraksa-Internal` matches in fixed time; otherwise it answers 403 `admin.internalHop` and rewrites nothing. It takes one value and never a chain: the client address from `X-Forwarded-For` (unknown, never loopback, when absent, repeated or comma-separated), the scheme from `X-Forwarded-Proto` (`http`/`https` only), the host from `X-Forwarded-Host`. `Connection.RemoteIpAddress`, `Request.Scheme` and `Request.Host` then drive the sign-in throttle, audit `ClientIp`, CSRF's origin check, HSTS and the response `Secure` cookie, all of which therefore follow the public scheme and host. Every other listener (the main admin port, the loopback plain-HTTP fallback listener) ignores these headers as before, and the loopback plain-HTTP fallback listener's DNS-rebinding `Host` check does not apply to the internal admin listener.
- **Allowlist.** On the main admin port `Paduraksa:Listen:AdminAllowedSources` still runs per connection, before TLS. On the internal admin listener the peer is always the process, so the same list is applied per request to the **forwarded** client address (403 `admin.sourceDenied` when refused); a request without a usable forwarded address is unknown and therefore refused while the list is non-empty. The public host's own policies (IP allow list and rate limits today; more WAF policies with M6) are the primary gate for a proxied admin; the admin's list is a second, independent restriction. First-run setup (`GET`/`POST /api/v1/setup`) is refused on the internal admin listener (403 `setup.viaProxy`): setup is only reachable on the admin port or the loopback plain-HTTP fallback listener.
- **Session cookie.** `SessionCookieTransform` leaves `__Host-paduraksa-session` alone on an admin route (the admin is its destination) and still removes it from every other upstream. A response transform removes a `Set-Cookie` for that name coming back from any non-admin upstream, so an upstream on the same name can't plant a session over the owner's (cookie tossing); the admin's own `Set-Cookie` passes. Both work on the header collection the transform stage actually exposes (`HeadersCopied`).
- **Admin host in the config.** `kind: admin` through the existing `/api/v1/hosts` endpoints. At most one admin host exists (`host.admin.duplicate`); it has no routes (`host.routes.unexpected`), redirect or respond; its certificate binding can't be `none` (`host.admin.httpsRequired`) and the mapping forces the HTTPS redirect regardless of the settings layers. It has no upstream of its own: every path goes to `__admin`. Its profile, IP allow list and TLS settings are the usual host layers. A disabled admin host is allowed (staged), but the guard below treats losing the only enabled one as cutting access.
- **Lock-out guard.** A command whose `CommandOrigin.AdminRequest` is set (authenticated on the internal admin listener) carries the caller's public host, scheme and resolved client address into Application. The command pipeline compiles the candidate and runs the caller's own request through the real `GateSimulator`; the change is refused with 422 `host.admin.lockout` unless the outcome is a forward to the admin route. That catches deletion, disabling, a kind change, a rename, a host/policy change that excludes the caller, a non-covering certificate, and a trusted-proxies change; a replace/rollback that recreates the admin host under a new ID but keeps it reachable is allowed. The CLI, the normal admin port and the loopback plain-HTTP fallback listener carry no `AdminRequest`, so they need no force. `?force=true` on the API (or `ConfigCommand.Force` on any command) is the explicit override, except that removing the admin's HTTPS stays invalid because an admin host is defined as HTTPS-only (the validator refuses mode `none`). Dry runs pass through the same check, so a preview reports the refusal too; a draft simulation (`PlanDraftAsync`) does not, so a what-if trace is never replaced by a lock-out. The audit event records `force` and `viaAdminProxy` in its details. **Modelling limits:** the probe is a `GET /` over the caller's host, scheme and resolved client address, not the actual path/method, and a change to the trusted proxies is refused outright while the request arrives through the proxy (the caller facts cannot faithfully model the new proxy chain). The rule is before/after: a condition that already fails the probe (a Specific certificate not covering the name, an existing modelling gap) does not block unrelated commands; only one that currently forwards and would stop doing so does.
- **Simulator.** `GateSimulator` runs the same `Decide`; the admin route is traced as "forwarded to the admin app" (`GateUpstream.Admin = true`, cluster `__admin`) instead of naming a user upstream, and the route-match step says the admin route takes every path. The parity suite includes an admin host.
- **Tests.** `AdminThroughProxyTests` (real host and real sockets) covers the sign-in flow and `/api/v1/auth/me` with a cookie through the public listener, CSRF against the public and a foreign origin, the cookie reaching the admin but not another upstream and a throwing `Set-Cookie` being stripped, the per-IP throttle seeing two forwarded clients separately, client-sent `X-Forwarded-*` being overwritten (and ignored on the admin port), the socket's 0600/0700 modes and reachability only through the admin host, a real WebSocket upgrade, the lock-out guard and `force`, and deletion over the normal admin port. `AdminHostLockoutTests` covers the simulation-based guard (delete, disable, rename, host/profile policy, kind, rollback, recreate-under-new-ID, trusted proxies and force); `AdminInternalListenerTests` the socket choice, live-socket refusal, symlinked run directory, secret and fallback; `AdminForwardedHeadersTests` the comma/repeated/mapped/proto and missing-secret cases; the compiler, validator and simulator tests cover `Kind = Admin`. The TCP fallback mode is exercised end to end, including the no-secret 403.

## 4. Typed IDs

### 4.1 Declaration

```csharp
[TypedId("host", IdKind.UuidV7)]   public readonly partial record struct HostId;
[TypedId("usr",  IdKind.UuidV7)]   public readonly partial record struct UserId;
[TypedId("chl",  IdKind.UuidV4)]   public readonly partial record struct PowChallengeId; // public-facing, no timestamp leak
[TypedId("aud",  IdKind.Int64Ordered)] public readonly partial record struct AuditEventId; // high-volume
```

The generator emits for each:
- `Value` (`Guid` or `long`), `New()`, `Empty`/`IsEmpty`, `static abstract` contract `ITypedId<TSelf>`
- `ToString()` → `host_0J9zb3xQk1Lr8m2V7aYc4D`, plus `ISpanFormattable`, `IUtf8SpanFormattable`, `ISpanParsable`/`IUtf8SpanParsable` (prefix-validated, allocation-free)
- `System.Text.Json` converter (registered in a source-gen `JsonSerializerContext`), `TypeConverter` (Blazor routing and Minimal API binding), YamlDotNet converter
- EF Core `ValueConverter` + `ValueComparer`, applied by **convention** (`ConfigureConventions` → `AddTypedIdConventions()`, which recognizes `ITypedId<,>` member types during EF's property discovery), so no per-property config
- OpenAPI schema transformer: `{ type: string, pattern: "^host_[0-9A-Za-z]{22}$", example: ... }`

### 4.2 Representations

| Kind | Use for | String form | DB storage |
|---|---|---|---|
| `UuidV7` (default) | All config entities, users, tokens, revisions, certs, orders | `prefix_` + 22-char base62 | 16-byte **BLOB, big-endian** (generated by our own RFC 9562 `UuidV7Generator`, which uses a 12-bit per-millisecond counter so IDs created within one ms still sort in creation order; `Guid.CreateVersion7()` fills those bits randomly and is banned. Written with `Guid.TryWriteBytes(span, bigEndian: true, out _)`) so byte order = time order and indexes stay append-mostly. Never EF's default TEXT GUIDs. |
| `UuidV4` | IDs that are publicly visible where creation time shouldn't leak (challenge IDs, share links) | `prefix_` + 22 base62 | 16-byte BLOB |
| `Int64Ordered` | High-volume append-only tables (audit events, metric rollups, access-log index) | `prefix_` + 11 base62 | `INTEGER PRIMARY KEY` (SQLite rowid: clustered, fastest). Layout: 44-bit ms timestamp (epoch 2025-01-01 UTC) + 19-bit monotonic counter seeded randomly at startup, sign bit always 0. Parsing rejects values above `long.MaxValue`. **Predictable, so internal/admin-only:** never use it for anything exposed publicly. Collision-free on a single node, provided the Data layer seeds the generator at startup with `Int64OrderedIdGenerator.Observe(MAX(id))`, which protects against a clock that's behind the last persisted ID. |

Base62 uses the alphabet `0-9A-Za-z` (ASCII order), **fixed width and left-padded**, so ordinal string sort equals numeric sort. Sorting IDs as strings in the UI or API gives the same order as the DB.

Generator notes (M0):
- Generated `New()` uses the process-wide generators on `TimeProvider.System`. Decided in M2: `Shared` stays there; `TimeProvider` *is* the clock abstraction, and code that needs a controllable clock (tests, the audit log and revision store) creates its own generator on its own `TimeProvider`.
- Every **source-generated** `JsonSerializerContext` that serializes typed IDs must register `TypedIdJsonConverterFactory` via `[JsonSourceGenerationOptions(Converters = [typeof(TypedIdJsonConverterFactory)])]`. The STJ source generator can't see the `[JsonConverter]` attribute our generator emits, and without the factory IDs serialize as `{}`.
- The generator is added as an analyzer to every project through `Directory.Build.props`. Prefix uniqueness is checked per compilation (PDKID004) and across all src assemblies by an architecture test.
- EF value converters can't call static abstract members inside expression trees (CS8927). Generic converters go through a plain generic helper (`static T Wrap<T, TV>(TV v) => T.FromValue(v)`).
- EF mapping (S4, `Paduraksa.Storage.Ids`): `configurationBuilder.AddTypedIdConventions()` swaps in a `PropertyDiscoveryConvention` that accepts typed IDs, so they're found from the model's own CLR member types (no scanning or type lists) in entities and complex types, as keys, FKs and nullables. Typed-ID properties are `ValueGenerated.Never`. **Inside JSON complex types IDs are stored as their canonical string** (`host_...`), not BLOB/INTEGER: the document stays readable and JSON members compare against a string parameter. ID lists (`List<RouteId>`) are primitive collections of canonical strings, as a column or inside JSON. Owned types mapped to JSON are rejected at model build; use complex types. **Hard rule: a JSON ID (TEXT) never equals a column ID (BLOB/INTEGER) in SQL**, so references inside JSON settings are resolved in memory by the compiler, never joined or compared in SQL. LINQ `==`/`!=`/`<`/`>`/`CompareTo`/`Contains`/`OrderBy` on IDs translate; `id.Value` doesn't (EF can't see through a converter).

### 4.3 Secrets that look like IDs (but aren't)

API tokens: `pdk_<tokenId base62>_<32 random bytes base62>_<crc32 base62>`. The prefix and checksum let secret scanners (GitHub, gitleaks) detect leaked tokens. The DB stores `tokenId` and `SHA-256(secret)`. A fast hash is fine for 256-bit entropy, and lookup by ID makes verification constant-time. Session cookies are opaque random 256-bit values with only the SHA-256 stored. **Decided in M4: no ASP.NET Data Protection around the cookie value.** It is already unguessable and stored hashed, so a key ring would add rotation to manage and no security; the Data Protection key ring in the vault arrives with antiforgery and Blazor in M5. A session ID (`ses_`) is UuidV4 (a handle shown in the session list that should not tell when the session began; the cookie value is the credential).

## 5. Data model (SQLite, EF Core 10)

Two database files, **deliberately separate**:
- `data/paduraksa.db`: config, users, revisions, audit, metric rollups. Owned by `Paduraksa.Data`. Both databases share the typed-ID conventions, SQLite pragmas and timestamp storage from `Paduraksa.Storage`.
- `data/vault.db`: encrypted key material and secrets. Owned **only** by `Paduraksa.Vault`, through its own internal DbContext. Backing up or exporting config never sweeps up keys by accident.

SQLite settings: WAL, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout`. A single writer is fine because all writes go through the Application layer. Reads use `IDbContextFactory` (also required for Blazor Server).

### 5.2 Identity & governance

| Entity | Notes |
|---|---|
| `User` (`usr_`) | Username, display name, password hash (ASP.NET `PasswordHasher` v3 PBKDF2-SHA512 or Argon2id), TOTP secret **ref** (vault), lockout, disabled |
| `Passkey` (`pk_`) | WebAuthn credentials (public keys only, so these live in config DB). Built on .NET 10 passkey primitives. |
| `RoleAssignment` | User ↔ Role (Owner, Admin, Operator, Viewer, Auditor), scope = global (per-tag scopes later) |

| `AuditEvent` (`aud_`, Int64Ordered) | Timestamp, actor (user/token/system), channel (dashboard/api/mcp/cli/system), action, target typed-ID string, outcome, IP, details JSON, **hash chain** (`prevHash`, `hash`) for tamper evidence |

**As built (M4 identity core).** Tables `Users`, `RoleAssignments`, `ApiTokens`, `Sessions`, `RecoveryCodes` (config DB, migration `Identity`); passkeys are deferred to M5. Usernames are unique and case-insensitive (`NOCASE`, ASCII only: 3 to 64 of letters, digits and `. _ - @ +`). The password hash is `$pbkdf2-sha512$v1$i=<iterations>$<salt>$<hash>` (PBKDF2-HMAC-SHA-512, 210 000 iterations by default, 16-byte salt, 64-byte hash, constant-time compare); it is rehashed at sign-in when its iteration count is lower than the setting (a new algorithm or layout would be a new version tag), an unknown username costs a derivation against a throwaway hash, and the policy is a minimum length (12, counted in characters) with no composition rules. Roles are permission sets (`RolePermissions`): Owner everything; Admin config, certificates, providers, audit, simulate, user list; Operator config, certificates, provider reads, simulate; Viewer reads and simulate; Auditor reads and audit. Only Owner holds `users:write`, `vault:manage`, `tokens:all`, `sessions:all`. A token's scopes are permission names (`config:write`) and its effective permissions are the intersection with its owner's current ones, evaluated on every use; a token cannot issue tokens. Sessions: the cookie is 32 random bytes in base64url, only SHA-256 is stored, with absolute and idle expiry and a last-seen write throttled to once per `TouchInterval`; a password-only session is *partial* (short-lived) until the second factor completes it, and the cookie value changes when it does. Lockout: after `MaxFailedAttempts` consecutive failures (password, second factor, or a wrong current password at a sensitive step) the account refuses sign-in for `LockoutDuration`; every refusal answers `InvalidCredentials`, and failures are audited under the system actor with the account as target. The attempt is counted *before* it is evaluated, in one write transaction (`BEGIN IMMEDIATE`) that refuses a locked account, and re-checked (lock, disabled, second factor on) inside the success transaction, so parallel guesses cannot outrun the limit or sign in past a lock; a success clears the count. A lockout ends the user's sessions only where the attacker already holds the password: at the second factor, or at a sensitive step of a signed-in session (change password, TOTP enrol/disable, recovery codes) where a wrong current password counts too; a lockout at the password stage ends nothing, so someone who merely knows a username cannot keep signing the owner out. Unknown usernames are audited without the typed name (people type passwords there; the chain is permanent). Starting a TOTP enrolment, like disabling it and regenerating recovery codes, needs the current password; confirming the enrolment does not (the code from the authenticator is the proof). The last enabled Owner cannot be demoted, disabled or deleted. All identity events are audited in the transaction that makes them (`auth.login`, `auth.second_factor`, `auth.lockout`, `auth.logout`, `auth.session.revoke*`, `token.issue`, `token.revoke`, `user.*`, `setup.complete`).

### 5.3 Global defaults → profile → host → route

`HostSettings` is one record with every tunable as `Override<T>` (`Inherit` | `Value(T)`), stored as an EF Core 10 JSON complex type. New settings mean no schema migration, just a defaulted field. The **compiler** resolves the layers into a flat, fully concrete `EffectivePolicy`. IDs inside `HostSettings` (JSON, stored as strings) are resolved by the compiler in memory, never by SQL joins or comparisons against ID columns (§4.2). The dashboard shows where each value comes from ("inherited from Global" or "from profile *LAN only*") with a one-click "override here" or "reset to inherited".

Host kinds in v1: **Proxy** (YARP), **Redirect** (precomputed target), **Respond** (fixed status + body from the compiled snapshot, e.g. 404/410/"coming soon"), **Admin** (§3.1). Serving files from disk (**Static**) is **cut from v1**: it needs path-traversal, symlink, MIME and caching semantics designed properly. When it comes back, the plan is a chroot-like root under `data/www/<hostId>`, symlinks disabled, `PhysicalFileProvider` with `ExclusionFilters.Sensitive`, ETag/Last-Modified, precompressed `.br/.gz` siblings.

Examples of `HostSettings` fields: force HTTPS, HSTS, HTTP/2/3 enable, min TLS version, request body limit, header timeouts, upstream timeouts, compression, rate-limit policy, geo policy, IP access list, rule sets, auth provider, error page set, robots mode, security headers preset, websocket, buffering, custom request/response headers, `X-Forwarded-*` behaviour.

## 6. Config lifecycle: commands, revisions, snapshots

### 6.1 Write path (cold, may allocate, may lock)

```
Dashboard / API / MCP / CLI / YAML import
        │  (Contracts DTO + baseRevision)
        ▼
Application command handler
  1. authorize (role/scope)                     → 403 + audit
  2. load current config, apply mutation
  3. validate (field rules + cross-object: dup hostnames, dangling refs, cert coverage, regex compile w/ timeout)
  4. COMPILE a candidate RuntimeSnapshot in memory   ← fails here, nothing is persisted
  5. BEGIN TX: write entities, ConfigRevision(doc, diff), AuditEvent; check concurrency token; COMMIT
  6. PUBLISH (single writer, coalescing to the latest candidate; see §6.2):
     a. swap the YARP provider config, cancel the old change token
     b. await YARP ConfigurationApplied / ConfigurationApplyingFailed (matched by RevisionId, timeout → alert)
     c. capture YARP's new Endpoint objects into the candidate's slot → Endpoint table
     d. SnapshotStore swap                       ← atomic reference swap; requests see it from here on
  7. notify: change feed (dashboard live update)
```

- **Optimistic concurrency.** Each entity has a concurrency token, and commands carry `baseRevision`. Two admins editing the same host get a conflict dialog with a diff instead of a silent overwrite.
- **Dry-run.** Every command supports `dryRun: true`, which runs steps 1-4 and returns the diff plus validation results. The dashboard's "Review changes" sheet, MCP's `preview_*` tools and `import --dry-run` all use this.
- **Rollback.** Load an old revision's document, run it through the *import* path (validate, compile) and commit it as a **new** revision ("Rollback to #37"). History is never rewritten.
- **Diff.** Structural diff over the canonical document (stable ordering by typed ID), rendered as an object-level change list plus a YAML side-by-side view.
- YARP's own `IConfigValidator` runs in step 4, so an invalid YARP config fails before commit. YARP otherwise swallows invalid configs: it logs and keeps the old one.
- **Startup = recompile the latest revision.** The DB's latest committed revision is always the source of truth, and the process compiles it on every start. A crash between step 5 (commit) and step 6 (publish) therefore costs nothing except that the change goes live on the next start. (In-process, a failed publish after a commit is reported to the command, logged as an error and audited, with no retry: the commit stands, the previous snapshot stays live, and the next commit's publish or the next start makes the change live, since every snapshot is the whole config.)
- **Last-known-good.** After each successful publish, the compiled snapshot's *source document* is also written to `data/last-good.json`. This file is only a fallback: if the DB is unreadable or migration fails at startup, the proxy still comes up serving traffic while the admin UI shows a degraded banner. (As built, §6.4: also when the latest revision is corrupt or doesn't compile, or a startup publish fails; an empty database is restored from the file; `/readyz` stays ready with the body `degraded`; with nothing usable at all the start fails.)

### 6.2 RuntimeSnapshot (immutable, built once, read lock-free)

```csharp
public sealed class RuntimeSnapshot
{
    public required long Generation { get; init; }
    public required ConfigRevisionId Revision { get; init; }

    // Host resolution: exact names + wildcard suffixes, case-insensitive,
    // looked up via FrozenDictionary.GetAlternateLookup<ReadOnlySpan<char>>() → no string slicing.
    public required HostTable Hosts { get; init; }

    public required CompiledHost[] HostsByIndex { get; init; }     // dense index used by metrics arrays
    public required CertificateTable Certificates { get; init; }   // SNI → SslStreamCertificateContext (prebuilt chains)
    public required GlobalGate Global { get; init; }               // global IP deny trie, trusted proxies, conn limits
    public required IProxyConfig Yarp { get; init; }               // path-only routes + clusters, pure function of content
    public required Endpoint[] YarpEndpoints { get; init; }        // RouteSlot → YARP Endpoint, filled at publish step 6c
    public required DefaultHostBehaviour Default { get; init; }
}

public sealed class CompiledHost
{
    public required int Index { get; init; }                       // position in THIS snapshot only
    public required HostId Id { get; init; }
    public required MetricSlot Metrics { get; init; }              // stable across generations (§6.3)
    public required IRequestPolicy[] Policies { get; init; }       // ordered, already specialised
    public required ReadOnlyMemory<byte> RobotsTxt { get; init; }  // pre-encoded UTF-8, or empty = passthrough
    public required ErrorPages ErrorPages { get; init; }           // pre-rendered byte segments
    public required RedirectSpec? HttpsRedirect { get; init; }
    // ...
}
```

`SnapshotStore` is just `volatile RuntimeSnapshot _current` plus `Publish` (Interlocked.Exchange, then fire change token). Each request reads the reference **once** at the start and uses only that snapshot, so a request never sees half of one config and half of another.

YARP integration (decided by spike S2, `docs/spikes/S2-yarp-reload.md`): **the gate picks the YARP endpoint itself, and ASP.NET routing never matches hosts.**
- **IDs:** YARP route, cluster and destination IDs are stable typed-ID strings, with no generation or revision in them. The YARP config is a **pure function of content**, so an edit that only touches policy is a YARP no-op and costs ≈ nothing.
- **Routes carry no Host match.** Each YARP route is path-only (or a catch-all per cluster) and exists only to give YARP an endpoint with the right cluster and transforms. Host-header matching was ~90% of the reload cost (500 hosts: 15 ms → 1.9 ms; 2000 hosts: 64 ms → 11 ms).
- **The gate resolves host and route** from its snapshot `S` (a per-host ordered route list: prefix/exact/regex, NPM-style `Order`). It takes the policies **and** the YARP `Endpoint` from the same `S`, then calls `HttpContext.SetEndpoint(...)` *before* `UseRouting`, so endpoint routing skips matching. A request therefore can't mix generations, and there is no version check, no snapshot ring and no 503 path. It costs 0 B in the gate. S2 measured gate entry → proxy pipeline at 152 B/request, against 256 B with Host matching.
- **Publish order** (§6.1 step 6): YARP applies first, then the endpoint table is captured from `EndpointDataSource` (keyed by route ID), then the snapshot is swapped. Until the swap, requests keep using the old `S` with its old `Endpoint` objects. S2 showed those keep proxying correctly even after YARP removed or replaced them, following YARP's live cluster state, so in-flight requests are fine.
- **Custom pipeline:** we use `MapReverseProxy(Action<IReverseProxyApplicationBuilder>)`, which replaces YARP's default pipeline, so **session affinity, load balancing and passive health must be added back explicitly** (`UseSessionAffinity()`, `UseLoadBalancing()`, `UsePassiveHealthChecks()`). Without them, passive health silently does nothing.
- **Client reuse:** a custom `IForwarderHttpClientFactory` must reuse the existing client when cluster config is unchanged. A new `HttpClient` counts as a cluster change and rebuilds every route on it.
- `ConfigureEndpoints` metadata is **not** used. S2 showed YARP only re-runs it for new or changed routes, so unchanged routes would keep stale metadata.

As built in M1 (`src/Paduraksa.Proxy`: `Snapshot/`, `Gate/`, `Yarp/`, `Config/`):
- **Types (M2):** the config model and the snapshot are keyed by typed IDs (§4): `Revision` is a `ConfigRevisionId` (`Empty` when there is no committed revision: the bootstrap snapshot, the empty startup config), `CompiledHost.Id` / `CompiledRoute.Id` are `HostId` / `RouteId`, and upstreams, destinations and certificate bindings use `UpstreamId` / `DestinationId` / `CertificateId`. YARP's route, cluster and destination IDs are their canonical strings (`rte_...`, `ups_...`, `dst_...`), formatted by the compiler; nothing on the request path formats an ID. YARP compares IDs ignoring case, so the compiler rejects route, upstream and destination IDs that differ only in case. `RuntimeSnapshot.Yarp` holds the YARP *content* (`YarpConfig`); the `IProxyConfig` with its change token and a unique `RevisionId` is created per publish by the provider. `Certificates` (`CertificateTable`) and `TrustedProxies` (`TrustedProxyPolicy`) are typed slots the compiler fills; `SnapshotStore` is the TLS selector's `ICertificateTableSource`, so a publish hot-swaps certificates for new handshakes.
- **Unbound → bound:** the compiler produces a candidate with generation 0 and no endpoints; the publisher `Bind`s it to YARP's endpoints and the next generation. The store starts at a bootstrap snapshot (generation 0, 503 for everything), so `Current` is never null.
- **Routes:** exact or segment-aware prefix, ordered by `Order`, then as listed; first match wins. **Match leniently, forward unchanged:** matching (and later path rules) uses a canonical *matching view* of the decoded path: `\`, `%2F` and `%5C` separate segments, repeated `/` collapse, `;...` segment parameters are dropped, trailing `.` and spaces are trimmed per segment, dot segments resolve, case is ignored. Many upstreams read those spellings as the same path, so `//admin`, `/admin;x`, `/admin.` or `/ADMIN` must hit the policies of `/admin`; over-matching only makes a policy stricter. The view costs 0 B (as is when already canonical, else on the stack, or a pooled buffer past 256 chars; Kestrel's request-line limit bounds it). The compiler rejects route paths that are percent-encoded or not canonical. Routes carry **only their own** policies. YARP routes are `/.paduraksa/r/{routeId}/{**rest}`, and the proxy pipeline rejects (404) any request whose endpoint the gate didn't set, so they can't be reached directly.
- **Forwarding:** the upstream gets the path exactly as received: a YARP request transform builds the URI from the raw request target (path part) plus the query, without re-escaping. YARP's default would turn `%2F` into `%252F`. M1 strips no prefixes.
- **Publisher:** single writer; a queued candidate is completed as `Superseded` when a newer one arrives. YARP's `IConfigValidator` plus a route → cluster check run first (`Invalid`). Content equal to what YARP runs skips the YARP round trip (policy-only edits). `ConfigurationApplyingFailed` → `Rejected`, and the previous YARP config is re-applied so provider and YARP agree; no outcome within `ApplyTimeout` (10 s) → `TimedOut`. On any failure the old snapshot stays live. **Before YARP exists** (the core host publishes first), an empty-YARP candidate publishes at once and any other waits for `MapPaduraksaProxy`, which validates it and hands it to YARP's initial load. Startup code therefore **never awaits** a publish: the core host's start returns before the public app starts, so it queues the publish and `/readyz` (`HasPublished`) reports when it's live. Disposing the publisher (shared-services disposal) stops the writer and fails anything queued or in flight.
- **Fixed answers** (Respond hosts, policy responses) with status 204, 205 or 304 must have an empty body (compile error otherwise) and are sent without `Content-Length`.
- **Default host:** 404 (default), 421, or close (abort: H1 closes the connection, H2/H3 reset the stream). The HTTP→HTTPS redirect is 301 for GET/HEAD and 308 otherwise; its `Location` (request host + raw target + public port) is the one string a gate-answered response allocates, built after the decision.

### 6.3 State that survives a publish

Snapshots are immutable and are thrown away on every publish, so **mutable runtime state must never live inside one**. Otherwise every config edit would silently reset rate limits and break metric series. Long-lived state sits in process-lifetime singletons (`RuntimeState`). Snapshots only hold *keys* into it, and those keys are derived from **stable identities**, never from array positions.

| State | Lives in | Keyed by | On publish |
|---|---|---|---|
| Rate-limit buckets | One global fixed-size bucket table (§7.3) | key long = **16-bit policy slot** (stable, from an append-only `RateLimitPolicyId → slot` registry, like metric slots) + **48-bit hash** of the partition key (IP/64, IP+path, header) | Carried over untouched. If a policy's rate/burst changed, the new parameters apply on each bucket's next touch (tokens clamped to the new burst). Deleted policies' buckets are cleared by the sweeper (unknown slot means clear). |
| Per-IP connection counts | Global connection table | client IP | Not snapshot-related at all. Only the *limit* comes from the snapshot. |
| Forward-auth decision cache | Per-provider caches | `AuthProviderId` + provider **config hash** | Kept if the provider's effective config is unchanged, otherwise dropped (a changed auth config must never reuse old decisions). |
| Basic-auth verify cache | Global | `AccessListId` + config hash + credential hash + IP | Same rule as forward-auth. |
| Metrics counters/histograms | `MetricsRegistry` | **`MetricSlot`**, allocated per typed ID (`HostId`, `RouteId`, `UpstreamId`, `DestinationId`) by an append-only slot registry | The compiler asks the registry for each ID's slot, so the same host keeps the same slot forever. Slots of deleted objects are freed after a grace period (one rollup interval). |
| Persisted metric rollups | SQLite | **typed ID** + timestamp, never slot or index | n/a |
| YARP health state | YARP (per destination) | ClusterId + DestinationId (typed-ID strings) | Verified in S2: state survives every reload that keeps the IDs, including changes to the cluster's own policies. **Pitfalls:** removing and re-adding a destination resets it to *Unknown*, which YARP treats as routable, and changing a destination's address under the same ID keeps the old verdict. So rollback and import must keep destination IDs. Optionally, key destinations as `{DestinationId}~{hash8(Address, Host, Health)}` so an address change gets fresh state. This only fixes a stuck passive-unhealthy verdict, since the new key starts as Unknown, and it resets affinity for that destination. |
| ACME HTTP-01 tokens | `IAcmeChallengeStore` | token | Independent of config snapshots. |

Spike S6 turns this into a test: N generations are published under load, and it asserts that rate-limit decisions, counter totals and YARP destination health are all continuous. M1 covers YARP health and request errors (`StateContinuityTests`); rate-limit and counter continuity are tested when those tables exist (M6, M7).


### 6.4 M2 build decisions

These refine §5 and §6.1 for the M2 build.

- **The config document is the source of truth.** `ConfigDocument` (in `Paduraksa.Contracts`, `apiVersion: paduraksa.dev/v1`) holds the global settings, profiles, upstreams and hosts with their routes. It contains references only, never secrets. Each revision stores it as canonical JSON (deterministic bytes), Brotli-compressed, with the SHA-256 of the uncompressed bytes. Startup, rollback, diff and export all read documents.
- **The EF config entities are a projection of the latest revision.** They are written in the same transaction as the revision, and serve queries (dashboard lists, "which hosts use this upstream") and DB-level invariants: a unique `COLLATE NOCASE` host name and foreign keys. Nothing reads them to rebuild config.
- **Host names are natural keys.** Each is stored normalised (§5.1), with no `hn_` ID.
- **Concurrency.** Every top-level object (global settings, profile, upstream, host) carries a `Version` that the pipeline increments on change. A command names the version it edited, so two admins editing different hosts never conflict. Whole-document commands (import, rollback) name the `baseRevision` and need it to be the latest. One writer at a time (`SemaphoreSlim`) in the Application layer.
- **Settings layering.** `HostSettings` fields are nullable; null (absent in JSON) means *inherit*. The compiler resolves built-in defaults → global defaults → profile → host → route (routes carry the route-level subset) into the concrete `ProxyConfigModel`. Nested settings (TLS) merge field by field; list-valued settings (an IP allow list) replace as a whole.
- **Errors carry a path.** Validation and compile errors carry a JSON-pointer path into the document (`/hosts/3/routes/0/path`), a stable code and a message, so every surface can point at the field.
- **Audit hash chain.** `hash = SHA-256(prevHash ‖ canonical bytes of the event)`; the first event's `prevHash` is 32 zero bytes. A verifier walks the chain in ID order and reports the first break.

As built in M2 (`src/Paduraksa.Application/Compilation`):
- **Mapping.** `ProxyConfigMapping.Map` is a pure function from the document's canonical form to `ProxyConfigModel`, so two spellings of one config compile alike. `ConfigCompiler` (the `IConfigCompiler`) runs it and `SnapshotCompiler` with the process's `SnapshotCompilerOptions`.
- **Layering.** Per host: built-in defaults → global defaults → its profile (a missing profile adds no layer; the validator rejects it, `host.profile.unknown`) → the host; per route, its allow list on top of the host's result. A null field inherits. TLS merges field by field. The IP allow list replaces as a whole, and an empty list means no restriction, which is how a layer (or route) lifts an inherited list. `ForceHttps` is judged after layering.
- **Allow lists: host chain and route chains.** The gate runs the host chain before the HTTPS redirect, fixed answers and route matching, so a route override can't *replace* a list that sits there alone. When every route ends up with the same list (none overrides the host's, or all override it alike), or the host has no routes, that list goes in the host chain only and guards everything the host answers. Otherwise each route carries its own effective list (the host's or its override), and the host chain carries the **union** of the routes' lists, dropping denied requests only if every route drops: a client no route admits is blocked on every path, over plain HTTP too (no redirect, no 403-vs-404 to map the host by, and a dropping host still looks dead), while one that some route admits is judged again by the route it hits. If some route is unrestricted the host chain carries no list, since anyone may reach that route. So a route can tighten, lift, or add a list. A test drives the real gate over generated documents (scheme x path x client IP) against a reference that reads the document directly.
- **For M6.** IP access must keep running ahead of the other host-level policies (forward-auth and the like), so an outsider never reaches them. M6 should also revisit matching the route before the HTTPS redirect, which would let per-route lists guard the redirect without the union.
- **Certificate binding (as built in M2; M3 resolves it against the inventory, §9.2).** Auto → no certificate of its own (the default one); Specific → its `CertificateId`; None → `HostSpec.Https = false`: no certificate-table entries and no `Alt-Svc`, and the gate answers HTTPS requests for the host 421 (a connection on the default or another host's certificate can't reach it). None with an effective `ForceHttps` is an error (validator: `host.certificate.noneWithForceHttps`; compiler at the host). Disabled destinations are left out; an upstream may have none left until an enabled host routes to it.
- **Compile errors carry paths.** `SnapshotCompiler` attributes each error to a host, route, upstream, destination (by typed ID) or the defaults/trusted proxies; `ConfigCompiler` maps that to a pointer into the document *as given* (`/hosts/{i}`, `/hosts/{i}/routes/{j}`, `/upstreams/{k}/destinations/{m}`, `/settings`, `/settings/trustedProxies`) with code `compile.failed`, each (path, message) once. An inherited value is reported where it is used (each host or route whose chain carries it); a duplicated ID points at its last occurrence. The mapping itself reports the few invalid values the model can't carry (an undefined certificate binding mode or load-balancing policy, a respond host without a content type). A test runs sample, edge and generated documents through the validator and the compiler: whatever validates must compile (certificate references aside, which only the compiler can resolve against the inventory, §9.2).

As built in M2 (`Paduraksa.Application.Commands.ConfigService`, commands and results in `Paduraksa.Contracts.Commands`):
- **Versions are revision numbers.** A revision gives every top-level object it changes (a route or destination change counts for its parent) its own `Seq` as the new version; untouched objects keep theirs, whatever a command sends. A version is therefore issued once, ever, and stays at most the latest `Seq`: a rollback to #37 committed as #52 gives what it changes version 52, so an editor holding any older version of those objects (including one from #37, or of an object deleted and restored) gets a conflict, while editors of objects the rollback leaves alone don't.
- **The empty config** is the default document with no revision. Startup writes nothing; the first command creates revision #1, and a whole-document command on an empty database names no base revision.
- **Errors** of whole-document commands point into the document as sent (a rollback: as stored). Object commands report the sent object's errors relative to it (`/names/1`), and errors the change causes elsewhere (a deleted upstream still in use) as related errors pointing into the canonical document after the change, like the change list. The sent object is validated last in its list, so a clash with another object is reported on it.
- **Commands that change nothing** (equal canonical config) commit nothing and return `unchanged`.
- **Audit:** commits in the commit's transaction; denied, invalid, conflict and not-found commands in a transaction of their own, written without the caller's cancellation once decided, a failed write logged rather than replacing the result; a publish failure after a commit as `config.publish` (failed), also when it happens after the command stopped waiting. Dry runs and no-ops aren't audited.
- **Publishing:** queued with the publisher under the writer lock, so snapshots go live in commit order; the command waits for the outcome outside the lock (bounded, then `pending`). A superseded publish reports the outcome of the newer publish that carries it. A failed publish is reported, logged and audited by the command whose publish it was; the commit stands, with no retry.
- **Another writer** (a second process on the same file) that commits between a command's load and its commit is seen inside the commit transaction; the command is prepared once more on the new head, and a second move is a conflict naming the real head.
- **Projection:** rewritten per touched object (delete its rows, insert them again) from the change list, with foreign keys deferred to the commit; the settings row names the revision the projection shows, and a projection that doesn't show the parent revision is rewritten whole. Host names are projected for every host with a copy of the host's `Enabled`, unique (`COLLATE NOCASE`) through a partial index over enabled hosts.

As built in M2 (startup: `ConfigService.StartAsync`, `Paduraksa.Application.LastKnownGood`; composition: `Server/Hosting/ConfigStore`, `ConfigStartup`):
- **Composition.** The config database (`<data dir>/paduraksa.db`), its context factory, the compiler (`ConfigCompiler` on `PublicListenerSetup.CompilerOptions`), the `LastKnownGoodFile` and the one `ConfigService` are shared instances, registered into all three hosts. The factory and the service come from a small private container (EF's factory and the service are meant to be resolved), which `SharedServices` owns and which alone disposes them. Disposal runs in reverse creation order after every host has stopped: the container (the service refuses new commands), then the publisher (stops its writer and fails whatever is queued, so nothing goes live after it), then the last-known-good file, created before the publisher (waits for its pending write); so the file never trails the last revision that went live. Certificate bindings resolve against the certificate inventory (§9.2); the placeholder certificate is its fallback default (§3).
- **Startup recompile.** The core host's `ConfigStartup` creates the data directory and runs `StartAsync` under the writer lock: migrate (`ConfigDatabase.InitializeAsync`), read the latest revision (none: the empty config), rewrite the projection whole if its settings row doesn't name that revision or can't be read (a restored or hand-edited database; any failure is logged and startup goes on, since the projection only serves queries and the next commit rewrites it anyway), compile, and queue the publish **without awaiting it** (as in M1: YARP attaches only when the public app starts). The outcome is logged when it arrives; a superseded startup publish (a commit's newer publish carries the config) isn't a failure.
- **Last-known-good** (`last-good.json`): `{format, revision, seq, sha256, document}`, the document being the revision's canonical bytes verbatim, so the hash is the stored `DocumentHash`; references only, no secrets. Offered after every successful publish (the startup one and each commit's, before the command returns) and written in the background, never under the writer lock; the newest offer wins, older ones are dropped. Each write goes to a new temp file with a random name (`CreateNew`, mode 0600 on Unix; leftovers of a crash are removed first, a symlink as a link), is flushed to disk and renamed over the target, which replaces a symlink there instead of following it. The directory isn't fsynced (.NET can't open a directory): safe but not durable, a power loss right after a write may leave the previous, still valid, file. A failed write is logged and never faults the writer. Reading uses one bounded read, refuses a symlink, checks format, IDs and hash, and never throws: a damaged file is logged as a warning (also on a healthy start) and replaced at the next publish. The empty config isn't written: it is no revision. One data directory serves one server process at a time (assumed, not enforced; the database tolerates another writer such as the CLI, this file doesn't).
- **Restore.** A database without revisions next to a usable last-known-good file has lost its config (a deleted or replaced `paduraksa.db`): the file's document is committed as revision #1 through the normal replace path (actor System, message "Restored from last-known-good #N (rev_...)", audited), logged at Critical, and startup goes on normally. If that commit is rejected or fails, the start is degraded on the last-known-good config (on the empty config if that doesn't compile either), accepting commands. To start over with an empty config, delete both files. A file newer than a database that has revisions (a restored backup) is only a warning: the database wins.
- **Degraded starts.** If the database can't be opened or migrated, or its latest revision can't be read (corrupt document, unreadable by this build, or columns a converter rejects: a damaged ID or timestamp), or it doesn't compile, the last-known-good document is compiled and published instead, logged at Critical, and `ConfigService.Status` says so (`Source = LastKnownGood`, the problem, the revision served). The store itself unusable: commands get `Unavailable` (`config.store.unavailable`, unaudited, since the audit log lives in that store) until the database is fixed or restored and the process restarted. Only the compile failed (say, after an upgrade made the compiler stricter): the database is fine, so commands are accepted and planned on the latest revision as always, and the first one that goes live ends the degraded state; refusing them would leave no way to fix the config short of editing the database.
- **A failed startup publish** (YARP rejects it or times out) leaves no live config. If the last-known-good file holds another revision and no command has committed since, that is published instead, degraded and accepting commands; otherwise the process stays up without a snapshot and `/readyz` says not ready, as in M1. (Tested with a publish the publisher refuses; every YARP setting the compiler emits is checked before YARP sees it, so no config makes YARP itself reject one.)
- **Readiness while degraded.** `/readyz` stays 200, with the body `degraded` instead of `ready`: the proxy serves traffic, and taking it out of rotation would turn a config-store problem into an outage. Keyword monitors can alert on the body; the cause is in the Critical log, and the admin UI shows the banner (M5).
- **Nothing to serve.** Neither a usable database revision nor a usable last-known-good document: `StartAsync` throws `ConfigStartupException` and the process exits 2 (startup failed), logged once at Critical by the host. An empty proxy that refuses changes would only look alive.
- **Change → live** through the whole process (real SQLite, YARP and Kestrel; one upstream and one host, two commits, until the first request for the new host comes back): median 11-15 ms on a dev machine with the rest of the suite running alongside.

## 7. Hot path

### 7.1 Budget & rules
- No DB, no `await` on anything except I/O to client/upstream, no locks (`lock`, `SemaphoreSlim`), no LINQ, no closures, no `string` building, no regex with backtracking.
- Per-request allocations in Paduraksa code: **0 B** steady state on keep-alive connections. Kestrel/YARP's own allocations are out of scope but measured. Enforced by benchmark tests asserting `GC.GetAllocatedBytesForCurrentThread()` deltas.
- Precompute everything at compile time: byte arrays for responses/headers, `SearchValues<string>` for substring sets, CIDR tries, country bitsets, redirect targets.
- Options validate themselves: an invalid value throws at `init` or construction, never later on the hot path (the snapshot compiler checks config first and reports it as an error).

**Spike S3 confirmed this** (`docs/spikes/S3-zero-alloc-gate.md`; .NET 10.0.13, YARP 2.3.0): the gate measured **0 B/request on H1 and H2** in every end-to-end run, taking 145-225 ns for the synchronous section. For realistic browser traffic, the costs we accept are:

| | B/request |
|---|---|
| Kestrel itself | ~1 KB |
| Routing + YARP hand-off | 152 B |
| Whole proxied request | ~4.1 KB on H1, ~4.4 KB on H2 |

Mechanisms M1 adopts:
- **Pipeline:** the public app is built on the **generic host with an explicit pipeline**: `Configure(app => { app.Use(gate); app.UseRouting(); app.UseEndpoints(e => e.MapReverseProxy(...)); })`, not `WebApplication`. YARP calls `AddAuthorization()` unconditionally, and `WebApplication` then auto-inserts `UseAuthorization()` *ahead of the gate*. That costs bytes and is a hazard if a `FallbackPolicy` is ever set. A guard test with a spy `IAuthorizationPolicyProvider` asserts it never runs.
- **Gate shape:** one synchronous gate middleware. It decides what to do, and the response body is written *after* the measured section. Responses come from precomputed bytes plus shared header values set through the typed header properties.
- **Per-connection state:** an immutable `ClientInfo`, set as a connection feature in `ListenOptions.Use`. It's shared by all H2 streams on the connection, so it must stay immutable. Never use `IConnectionItemsFeature.Items`, which is one non-thread-safe dictionary for all streams.
- **Per-request state:** one object cached in `IPersistentStateFeature` and reset each request. Stream reuse happens only on graceful end, so RST, cancels and Drop reallocate, and that's accepted.
- **Host lookup:** `Headers.Host[0]` (H2 `:authority` is already folded in), with the port stripped by span. Two `FrozenDictionary` tables (exact names, wildcard parents), `OrdinalIgnoreCase`, looked up via `GetAlternateLookup<ReadOnlySpan<char>>`: 11-22 ns, 0 B. `Request.Host.Host` allocates when a port is present. The compiler **rejects duplicate host names** (otherwise the last one silently wins) and canonicalises IPv6-literal keys.
- **Client-IP parsing:** our own span parser into `UInt128`. `IPAddress.TryParse` allocates 40/80 B. Ours is stricter than the BCL: no octal, hex, short forms, zone IDs or whitespace. M1 keeps the edge-case list plus a differential fuzz against the BCL.
- **Policies:** sealed `IRequestPolicy` classes returning a 16-byte `PolicyDecision` struct.
- **Tests:** `AllocAssert.Zero(state, static lambda)` for synchronous code, plus one in-process Kestrel test asserting gate bytes == 0. Kestrel and YARP numbers are tracked in `bench/`, not asserted.
- **Benchmarks:** they run under workstation GC, because BenchmarkDotNet's `Allocated` column is wrong under Server GC with the in-process toolchain. Non-monotonic `GC.GetTotalAllocatedBytes` samples are discarded.

```
   with Paduraksa transforms
   • X-Forwarded-*, X-Real-IP, request ID, security headers, custom headers (precompiled transforms)
   • forwarding headers as built in M1 (YARP's own X-Forwarded-* transforms are off), always OVERWRITTEN:
     X-Forwarded-For, X-Real-IP = exactly one address, the resolved client (no chain is kept or appended;
       IPv4 dotted quad, also for IPv4-mapped peers; IPv6 without brackets); left out if unknown
     X-Forwarded-Proto = the trusted request scheme from stage C (the same one the redirect uses)
     X-Forwarded-Host = Host / :authority as received, port included
     Forwarded, X-Forwarded-Prefix, X-Forwarded-Port = removed (only a client could have set them)
     every cf-* header (case-insensitive: CF-Connecting-IP, CF-Visitor, Cf-Access-Jwt-Assertion,
       Cf-Access-Authenticated-User-Email, cf-ipcity, ...) and True-Client-IP = removed unless
       CloudflareHeadersTrusted (Cloudflare mode and trusted peer); a trusted generic proxy doesn't qualify.
       One scan of the outgoing header names, 0 B. Otherwise a LAN client could forge Cloudflare Access SSO
       past a tunnel.
     The address string is cached on the pooled request state; the rest are constants or Kestrel's strings.
   • upstream errors / no healthy destinations → custom error pages

F. Telemetry (always on, lock-free): counters + latency histogram per host / status class / upstream
```

### 7.3 WAF building blocks (all compiled per snapshot)

| Feature | Implementation |
|---|---|
| IP allow/deny | `CidrSet` (M1): merged, sorted, disjoint `UInt128` ranges (IPv4-mapped), binary-searched, immutable. Chosen over a radix trie: membership needs no longest-prefix match, and the arrays are smaller and need fewer dependent loads (S3: 7.7 ns for 2,000 CIDRs). IPv6 rate keys are masked to /64 (`IpKey.MaskTo`). |
| Geo blocking | Country DB (DB-IP Lite: CC-BY, no key; MaxMind GeoLite2 optional with a license key) compiled into sorted range arrays and binary-searched. Country is resolved **once per connection** (or per request when behind a trusted proxy). Policy = `ulong[4]` bitset of blocked countries. DB auto-update job. |
| Rate limiting | Fixed-size open-addressed table (power of two, default 256 Ki entries ≈ 4 MiB). Each entry is two `long`s: a 64-bit **key fingerprint** (claimed with CAS, linear probing over at most 8 slots, else the oldest of those is evicted) and a packed **state** updated with a CAS loop. State layout: **bits 63-24 = last-refill time** in ms since process start (40 bits ≈ 34.8 years, so no wraparound handling needed); **bits 23-0 = tokens in 1/16 units** (unsigned 20.4 fixed point: max ≈ 1,048,575 tokens of burst, refill precision 1/16 token). The refill rate is a policy parameter in tokens/s, applied as `elapsedMs x rate x 16 / 1000` with saturation at burst. A background sweeper reads the **policy slot** from the high 16 bits of each key (the fingerprint itself can't be inverted, so the slot is stored alongside it). It looks up that policy's current full-refill window (burst / rate) and clears entries untouched for longer than that, or immediately if the slot no longer maps to a live policy. A 48-bit hash in a 256 Ki table makes false sharing between partition keys negligible (~2⁻³⁰ per probe). Bounded memory, so a flood of unique IPs can't exhaust RAM. Collisions only make limits slightly stricter. Policies per host or route: req/s + burst, keyed by IP / IP+path / header. Returns 429 + `Retry-After`. |
| Request size limits | `IHttpMaxRequestBodySizeFeature` per host/route. Header count/size and URL length are checked cheaply in the gate. Global Kestrel limits act as the outer bound. |
| Path deny rules | Exact/prefix in a trie. Glob compiled to a small matcher. Regex as an escape hatch: `RegexOptions.NonBacktracking` (ReDoS-safe) with a compile-time validation timeout. |
| User-agent deny | `SearchValues<string>` (vectorised multi-substring, case-insensitive), plus presets ("AI crawlers", "known scanners", "empty UA"). |
| Robots.txt | Per host: passthrough / managed (preset: disallow all, block AI crawlers, custom text). Served from pre-encoded bytes. |
| Error pages | Per status (and "upstream down" / "blocked" / "rate limited" / "maintenance"). Templates pre-split into byte segments at compile time, with variables (`{status}`, `{requestId}`, `{host}`) written straight into the response `PipeWriter`. **Replacing upstream error bodies** (opt-in per host) is decided at **response-header time** from status + content type. The upstream body is drained and discarded, never buffered. It's never applied to `101` upgrades, `text/event-stream`, gRPC (`application/grpc*`), or responses whose headers have already been flushed. |
| Maintenance mode | Per host, a toggle with a custom page and an IP bypass list. |

### 7.4 Observability (no locks on the hot path)
- **Counters:** `long[]` indexed by `metricSlot * K + metric` (stable slots, §6.3; never the snapshot's host index), striped per core (cache-line padded) to avoid contention. Summed only when read.
- **Latency:** fixed log-linear histogram buckets (≈ 1 µs → 60 s, ~120 buckets), updated with `Interlocked.Increment`. Two histograms are kept: total time and upstream time, so the proxy's own overhead is visible.
- **Exposed via** `System.Diagnostics.Metrics` (`ObservableCounter`/`ObservableGauge` callbacks read the arrays), so OpenTelemetry and Prometheus `/metrics` (admin port) work out of the box.
- **Dashboard live data:** a 1 s sampler writes into in-memory ring buffers (last ~1 h). A background job persists 1-minute rollups to SQLite **keyed by typed ID** (`HostId`, `UpstreamId`, ...), with configurable retention.
- **Upstream health:** YARP active (HTTP probe, interval, path, expected status) and passive (failure-rate) health checks. State changes go to the audit log + notifications and appear as dashboard status dots.
- **Access log (optional):** a fixed-size ring buffer of structs referencing existing strings (no copies), drained by a background writer to JSONL/CLF with rotation. It powers a **live tail** in the dashboard (filter by host/status/IP) and can be sampled.
- **Request ID:** `X-Request-Id` (honour incoming from trusted proxies or generate one), shown on error pages so users can report it.

### 7.5 HTTP/3 strategy

**Spike S1 (see `docs/spikes/S1-http3-sni.md`) showed that per-SNI selection and hot-swap work on Kestrel's QUIC listener in .NET 10**, through `ServerCertificateSelector`, `TlsHandshakeCallbackOptions` and `ServerCertificateSelectionCallback` alike. So every host that enables H3 gets it, and the single-H3-cert fallback isn't needed.

- **Listener layout:** two `Listen` calls on :443 (dual-mode `[::]`).
  - TCP: `Http1AndHttp2`, `DisableAltSvcHeader = true`, then the connection middleware (PROXY protocol, IP gate), then `TlsHandshakeCallbackOptions`.
  - UDP: `Http3` with its own `TlsHandshakeCallbackOptions`, which also performs the stage-A gate. It's added only if `QuicListener.IsSupported`.
- **Builder:** the public app runs on the generic host with `UseKestrelCore()`, which leaves out Kestrel's HTTPS configuration and the QUIC transport. `UsePublicHttpsTransports()` adds both (`UseKestrelHttpsConfiguration()` and `UseQuic()`); without them H3 listeners fail at startup. *Spike history:* S1 found this under `WebApplication.CreateSlimBuilder`, which has the same gap.
- **Still open:** a real browser upgrading to H3 (needs a trusted cert), routable IPv6, and arm64 libmsquic. Carrying the QUIC-callback ClientInfo through to the request works: a feature set on the QUIC connection context in the callback is visible to the H3 request (`PublicHttp3Tests`, Docker).
- **As built in M1:** `UsePublicHttpsTransports()` on the generic host's `UseKestrelCore()`, then `ListenPublicHttp` and `ListenPublicHttps` (§3). `run-quic-tests.sh` runs the QUIC tests of `Tests.Proxy` and an end-to-end H3 request through `PaduraksaHost` in Docker with libmsquic.
- **Either way, `Alt-Svc` is emitted by Paduraksa, not Kestrel.** Kestrel's automatic header is disabled (`DisableAltSvcHeader`). Our header is precomputed per host, only for H3-eligible hosts, using the **public** HTTPS port from settings (default 443), not the bound port. That way a port-mapped deployment can't advertise the wrong port.
- H3 is off globally if `libmsquic` isn't available (`QuicListener.IsSupported`). `paduraksa doctor` reports this. The stock `aspnet` image doesn't ship it: install `libmsquic` from packages.microsoft.com (≈ 21 MB incl. `libnuma1`; tested 2.6.3 on Ubuntu 24.04).

### 7.6 Client IP behind Cloudflare (native)

Many homelabs sit behind Cloudflare's proxy (orange cloud) or a Cloudflare Tunnel. Getting the real client IP must be a toggle, not a hand-maintained CIDR list. It's a built-in **trusted-proxy provider**, which the generic trusted-proxy model (CIDRs + header) and future providers also use.

- **Modes:** `Off` · `Proxy` (Cloudflare connects to us directly) · `Tunnel` (a local `cloudflared` connects to us). Set globally and overridable per host (§5.3); M1 has the global setting only (`DefaultsSpec.TrustedProxies`: mode, trusted CIDRs, generic header, `True-Client-IP` and X-Forwarded-For fallbacks), and the per-host override comes with M2/M6. The wizard asks "Is this server behind Cloudflare?" and offers to set it.
- **Who is trusted:**
  - `Proxy`: the TCP peer (after PROXY protocol, if any) must fall within **Cloudflare's published edge ranges**. These are shipped as a baked-in list and refreshed by a background job from `https://api.cloudflare.com/client/v4/ips`, falling back to `https://www.cloudflare.com/ips-v4` / `ips-v6`. They're stored with a fetch timestamp and compiled into the snapshot as a CIDR trie. A failed refresh keeps the last good list and raises a dashboard warning if it's stale (more than 30 days old).
  - `Tunnel`: the peer must be the configured `cloudflared` address (loopback, a Docker network CIDR or a specific IP). Edge ranges don't apply because the TCP peer is `cloudflared`.
- **Which header:** `CF-Connecting-IP` (single value, so there's no X-Forwarded-For chain parsing). Optionally `True-Client-IP` (Enterprise) or the right-most untrusted entry of `X-Forwarded-For` as a fallback. The value is parsed span-based into the same `UInt128` client-IP representation used everywhere, with IPv4-mapped addresses normalised. A missing or unparsable header from a trusted peer counts as a counter + debug log, and the peer IP is used.
- **Anti-spoofing:** when the peer is **not** trusted, **every `cf-*` header** (Cloudflare adds more over time, and Cloudflare Access's `Cf-Access-Jwt-Assertion` / `Cf-Access-Authenticated-User-Email` carry identity) and `True-Client-IP` are ignored, and they're **stripped before forwarding upstream**. Upstreams always get a clean `X-Forwarded-For` / `X-Real-IP` built from the resolved client IP (§7.2 E).
- **What the real IP feeds:** WAF IP allow/deny, geo, rate-limit keys, access lists, forward-auth headers, access logs, metrics. Connection-stage limits (§7.2 A) necessarily see the Cloudflare edge IP. They must therefore exempt trusted Cloudflare peers from per-IP connection caps, or every visitor would share a handful of edge IPs.
- **Optional extras (per host or global):**
  - **Geo from `CF-IPCountry`:** when the peer is trusted, use it instead of the local Geo DB lookup. It's free and accurate. `XX`/`T1` map to "unknown".
  - **`CF-Visitor` scheme:** the original scheme for the HTTP→HTTPS redirect decision when Cloudflare connects to the origin over plain HTTP ("Flexible" SSL, or `cloudflared` forwarding to port 80). This avoids redirect loops. Built in M1 (§7.2 C) and always on in the Cloudflare modes; Flexible is counted and logged once, and the dashboard (M5) will warn that it is insecure.
  - **Origin lockdown:** reject (or 403) requests on a Cloudflare-mode host whose peer isn't Cloudflare (or `cloudflared`), so the origin can't be reached by IP to bypass Cloudflare's WAF. It's enforced at the connection stage when *all* hosts on a listener require it.
  - **Authenticated Origin Pulls:** request a client certificate from Cloudflare and verify it against Cloudflare's origin-pull CA (shipped, replaceable) on the TCP listener (§7.2 B, per-SNI `ClientCertificateRequired`). This is the strong form of origin lockdown.
  - **`CF-Ray`** is recorded in access logs and offered as a variable on error pages, next to our request ID, so issues can be correlated with the Cloudflare dashboard.
- **Certificates:** Cloudflare Origin CA certificates can be uploaded like any other (§9), with a hint that they're only trusted by Cloudflare. DNS-01 via the Cloudflare DNS provider (§9) works whether or not the proxy mode is on.
- **Request simulator** (§7.7) takes a "via Cloudflare" toggle, so users can see which IP and country the policies would see.

### 7.7 Request simulator ("Why was this blocked?")

Admins test their rules before or after a change by asking what a request would get, and why. **The simulator runs the real gate code over a real compiled snapshot, never a reimplementation**, so its answer can't drift from what production does.

- **Input:** URL (scheme, host, port, path, query), method, headers (including the user agent and cookies), the peer IP plus how it arrives (direct, through a trusted generic proxy, via Cloudflare Proxy or Tunnel, with or without PROXY protocol), and the TLS context (the name sent in the handshake, ALPN/HTTP version, TLS version). The surfaces fill in sensible defaults, so a URL and an IP are enough.
- **Target config:** the live snapshot, any stored revision, or a *draft*: a document or pending command compiled through the dry-run path (§6.1 steps 1-4) and never published. So "what would this change do to this request" is answerable before committing.
- **Output:** the outcome (forward to upstream X / fixed answer / redirect / 421 / drop) plus the **trace**: client-IP resolution (which header and hop were trusted), host match (exact/wildcard/default), the TLS-policy check, each policy in order with its verdict and reason, the HTTPS redirect, route match (which route, and the matching view of the path), and the upstream (cluster and the destinations currently healthy; load balancing is random, so not which one).
- **No cost on the hot path.** Gate steps report through a tracer passed as a **generic struct type parameter**. Production uses a no-op tracer, which the JIT removes entirely; the simulator uses a recording one. The 0 B allocation tests and the gate benchmarks guard it.
- **Stateful and outbound policies (M6 on)** are simulated without side effects: a rate limit reports "would allow, N tokens left" without taking one; forward-auth reports "would call `<provider>`" (an explicit opt-in may make the real call); geo shows the country it resolved.
- **Parity tests:** for generated configs and requests, the simulator's outcome must equal the real gate's (the M2 `CompiledBehaviourTests` harness is the seed). Each policy added later (M6) must add its trace step and parity cases.
- **Surfaces:** one Application function, `SimulateAsync(target, request)`. It is exposed as `POST /api/v1/simulate` (M4), as the MCP `simulate_request` tool (M8), and in the dashboard simulator page (M5). Access-log entries link into it with the request pre-filled (M7).

**As built (M4, simulator core).** The tracer is `IGateTracer`, passed as a struct type parameter to the one decision body, `GateMiddleware.Decide<TTracer>(context, snapshot, clientAddresses, challenges, tracer)`; production's `Decide(context)` passes `NoGateTracer` (empty methods, so the JIT drops them), and the Kestrel 0 B tests plus a direct `Decide<NoGateTracer>` allocation test guard it. The gate reports client resolution (peer, source, trusted header, scheme source), the ACME hook, the host match (`HostTable.Find(..., out HostMatchKind)`), the TLS-policy check (`ConnectionTlsCheck.Check` names the 421 reason; `Satisfies` is `Check == None`), each policy by scope and index, the HTTPS redirect, fixed hosts, the route match with the canonical path, and the upstream hand-over. `Paduraksa.Proxy.Simulation.GateSimulator.Run(snapshot, probe, challenges, listeners)` runs the real `Decide` with the recording tracer, after the stand-ins for what the server does first, in the server's order: the listener's admission (`ProxyProtocolAdmission.Check`, the connection middleware's own decision, from `ListenerFacts`: a PROXY header the listener doesn't expect, a missing one, an untrusted socket, or no HTTP/3 listener is `ConnectionRejected`); the TLS handshake (`TlsHandshakeSelector.Select` over the snapshot's certificate table, which the listeners call too, plus the entry's own TLS-version and ALPN options: unknown SNI, HTTP/3 off, a TLS 1.2 client to a TLS 1.3-only name, the h2 to http/1.1 fallback); and Kestrel's request checks (`RejectedByServer`, 400: on HTTP/1.1 anything but exactly one valid `Host`; on HTTP/2 and HTTP/3 `:authority` is the host and a `Host` header is ignored; the path is percent-decoded except `%2F`/`%5C`, escapes that aren't UTF-8 stay as written, and dot segments are removed, all checked against the real server over sockets in `SimulatorSocketParityTests`). A snapshot not bound to YARP gets placeholder endpoints. Client resolution is `TrustedProxyClientAddressSource.ResolveCore` with no counters and no log line, so a simulation changes no counter. `RequestSimulator.SimulateAsync(target, request, origin)` (Application) takes live, `RevisionSimulationTarget`, `DraftDocumentSimulationTarget` (a `ReplaceConfigCommand` on the current head, retried once on a commit in between) or `DraftCommandSimulationTarget`; drafts go through `ConfigService.PlanDraftAsync`, which is `AttemptAsync` as a dry run that hands back its compiled candidate, so validation, certificate rules and compile errors are the real command's and are returned as `Invalid` with the dry run's errors, while a stale version or missing object is `DraftRejected`; a command that changes nothing simulates the head it planned on. The same checks that reading applies (`apiVersion`, null list elements) run on any payload first. A corrupt head, a degraded store or an unreadable database is `Unavailable` with a reason, never an exception. Nothing is audited, stored or published. Request limits are Kestrel's defaults (8 KiB request line, 32 KiB and 100 headers, a token method of at most 32 characters, no control characters in the query, no backslash in the authority) and a field that would change nothing (`transportIp` without PROXY protocol, `peerIp` on a direct request, `tls` on a plain-HTTP URL) is refused, not ignored. At most 4 drafts or revisions compile at once (`RequestSimulator.MaxConcurrentCompiles`); one that waits more than 2 s is `Unavailable`; the live target takes no slot. Authorization: `ISimulationAuthorizer` is asked for every target (see §10). Parity: `SimulatorParityTests` (Proxy: every outcome, 421 variants, all trusted-proxy modes and header shapes, PROXY protocol, ACME answered and fall-through), `SimulatedBehaviourTests` (Unit: 300 generated documents against the `GateHarness`), `SimulatorSocketParityTests` (real sockets) and end-to-end tests through a real host.

**Stateful policies must not mutate when simulated (M6 rule).** The simulator calls `Evaluate` on the live policy instances. `RequestView.IsSimulation` is true on that path and a constant `false` in production (a static abstract member of the tracer type, folded away by the JIT). A policy with state peeks: a rate limit reports "would allow, N tokens left" without taking one, a challenge issues no nonce, forward-auth starts no call unless the request opts in. Built-in policies are stateless today, so this is the seam plus the rule; each M6 policy adds its `Name`/`Explain` trace hooks and a parity case that checks it left its state alone.

Decisions and gaps. (1) **No key is loaded for a draft or a revision.** Whether a certificate is usable is decided from what the vault describes (`ICertificateCatalog.DescribeAsync`: public facts, no key opened): a certificate the vault doesn't hold, the local CA root, or a chain outside its validity period is unusable with the real loader's reasons (`CertificateInventoryLoader.ForSimulation` shares the validity logic), so a draft binding to one is refused as a real command refuses it, and Auto hosts pick the same certificate. Built-in (placeholder) certificates count as served by this process. What is served is a self-signed placeholder per ID (`SimulationCertificateSource`). The handshake step names the inventory certificate (`ServerCertificate.Id`, set by `CertificateInventoryLoader`; a context not built by the loader has an empty ID and isn't named). Without a catalog (no vault registered) every certificate the table calls valid counts as usable. When the certificate table can't be read the result says so. (2) **Destination health is live YARP state** (`IUpstreamHealth`, over `IProxyStateLookup`, attached by the public app through `DeferredUpstreamHealth`): a destination of the target config reports the live proxy's answer for the destination with that ID **and address**, `Unknown` otherwise, with a note (the "can't be known for a config that isn't live" note only for non-live targets); the destination that serves a request is never named. A destination the live proxy keeps out of rotation is `Unhealthy`; YARP counts a destination with no health data yet as available. (3) **The ACME HTTP-01 answer is traced for real**: `GateSimulator.Run` takes the live `AcmeChallengeStore` and the gate's own `TryAnswerAcmeChallenge` answers or falls through; challenges are process state, not config, so every target uses the live store. (4) Trace facts use stable camelCase wire names (`TraceNames`), policies name themselves explicitly (`static`, `ipAllowList`). (5) Per-host trusted-proxy overrides don't exist yet, and stateful or outbound policies (M6) aren't there to simulate. (6) The probe takes the HTTP and TLS versions as what the client negotiates; an HTTP/2 request to a name that offers only http/1.1 is reported as the HTTP/1.1 request it becomes. A request DTO can't say "no Host header" (the probe can). (7) An admin host's implicit route (PLAN §3.1) forwards to the admin app: the trace says so and `GateUpstream.Admin` is true with the `__admin` cluster, rather than naming a user upstream; the parity suite includes one. Not in M4 core: MCP and the dashboard page.

## 8. Vault (key-material trust boundary)

### 8.1 What it holds
TLS private keys (server certs **and** upstream mTLS client certs) · ACME account keys · EAB HMAC keys · DNS provider credentials · TOTP secrets · internal CA key · Data Protection key ring (the dashboard's antiforgery and circuit state) · PoW/forward-auth HMAC keys · basic-auth isn't a secret (hashes only).

### 8.2 Public surface (capability interfaces in `Paduraksa.Core`, all implemented `internal` in Vault)

Notes on the refinements:
- **Serving flow.** The snapshot compiler is synchronous, so Application preloads the serving contexts (`LoadForServingAsync`) for the certificate inventory (§9.1) before each compile and gives the compiler an immutable `IServerCertificateResolver` over them. The proxy never sees the source, and the vault returns the same context instance for an unchanged certificate (the proxy deduplicates by instance). The vault never disposes an instance it handed out; a replaced one is dropped and collected. The context's `TargetCertificate` carries the key, so the guard against exporting it is the key-material ban list (`BannedSymbols.KeyMaterial.txt`), not the type.
- **Caller-chosen IDs, atomic replacement, staged keys.** Every way of replacing a certificate (`AttachChainAsync`, import, self-signed, local-CA re-issue) keeps its `CertificateId` and swaps key and chain in one transaction, so Specific bindings survive renewals. `CreateKeyAndCsrAsync` stages a key and returns a `StagedKeyId` that `AttachChainAsync` must present; a stale token throws `StagedKeyMismatchException`.
- **Import.** PEM must carry a PKCS#8 key (plain or encrypted), otherwise PFX under the vault's own `Pkcs12LoaderLimits`; at most 1 MiB is read; every failure surfaces as `CertificateImportException` with a reason. The leaf is also refused if it is an RSA key under 2048 bits (`WeakKey`) or a CA certificate (`CaCertificate`); an expired leaf is accepted (the inventory treats it as unusable until renewed). "Usable name" is decided by `ICertificateNameRules`, implemented by the inventory's own normaliser (`CertificateNameRules`) and handed to `AddPaduraksaVault`, so the vault never accepts names the inventory drops (a vault built without one uses its strict rule). The KDF cost of an encrypted PKCS#8 is bounded before it runs (PBKDF2 or PKCS#5/12 iteration count at most 600000, else `Unreadable`) and runs once per key type the certificates could have (normally once); everything found wrong while reading the certificate's extensions after parsing is `Unreadable`, never an exception.
- **Certificate metadata.** `CertificateInfo` has the SHA-256 fingerprint, the serial number as the DER INTEGER content bytes (leading `00` kept), the Authority Key Identifier (with the serial it is the RFC 9773 ARI certificate ID) and the issuers of the chain (for `preferred_chain` selection). The subject has a CN only for a DNS name of at most 64 characters, otherwise it is empty.
- **JWS.** Acme writes the protected header and payload; the vault base64url-encodes, signs (ES256/ES384 as fixed-width `R||S`, RS256 as PKCS#1 v1.5) and returns the flattened-JWS pieces. It refuses a header whose `alg` is not the key's. EAB's inner JWS is built by Acme and signed with an `IMacKey` (HS256). Account key rollover is deferred (§9).
- **MAC keys.** The algorithm is fixed in the secret's metadata when it is stored, and `OpenAsync` checks the expected kind. A handle resolves the current version on every call; `Verify` also accepts the previous version for a grace window after a rotation, `Sign` never does.
- **Secrets carry their destinations.** `SecretOptions.AllowedHosts` (required for `DnsApiToken`) is set by the admin when creating the DNS provider and stored with the secret. The authenticating handler uses its intersection with the provider code's own `SecretInjection.AllowedHosts` (normalised host names, compared with `Uri.IdnHost`).
- **TOTP.** Since there is no get, M4's TOTP needs vault-side generation: the vault creates the secret, returns only the one-time provisioning URI for the QR code, and verifies codes itself.
  **As built (M4, `ITotpAuthenticator`).** `BeginEnrollmentAsync` generates 160 random bits, seals them as a `TotpSecret`, and returns the secret's ID and the `otpauth://` URI (a `Uri`: the one deliberate egress, once); `ConfirmEnrollmentAsync` turns a pending secret into a confirmed one with a code; `VerifyAsync` accepts codes for confirmed secrets only; `DeleteAsync` removes it. RFC 6238 with SHA-1, 6 digits, 30 s steps, one step of drift either way, every step compared in constant time. **Replay protection** is a `TotpStates.LastStep` column advanced by one conditional update, so a time step (and every earlier one) is accepted once per secret, across restarts, processes and simultaneous requests (vault migration `Totp`). No call returns the secret after enrolment, and the architecture test holds the contract to plain data. Recovery codes are not the vault's: ten 16-character codes (about 79 bits), shown once, stored as SHA-256 in the config DB, single use by one atomic update.
- **Async lookups, nullable misses.** `Describe` and the public-key lookups are async (they read the vault database), and a missing item returns `null`.

**As built (M3 vault certificates).**
- **Storage.** `CertificateKeys` holds one row per `CertificateId`: the PKCS#8 key sealed by the envelope cipher (AAD purpose `certificate-key`, or `certificate-key/local-ca` for the root, so a leaf row edited into the root fails to open), the public chain PEM (leaf first, intermediates, no root unless the certificate is its own root), a version that is both in the AAD and a concurrency token, and a unique-where-true `IsLocalCaRoot`. A replacement is an update of that row in one `SaveChanges`, which is what makes key and chain swap atomically. `StagedKeys` holds at most one row per certificate (the key sealed to its own `StagedKeyId`, plus the requested names): staging again updates the row in place, so the earlier token no longer names it. Every replacement route drops the ID's staged key in the same transaction, `DeleteAsync` takes both rows, and KEK rotation re-wraps both tables (counted in `KeysRewrapped`). `CertificateInfo` is recomputed from the stored chain; no metadata is duplicated.
- **Chains.** `AttachChainAsync` takes the first certificate as the leaf, requires its public key to be the staged key's and its SANs to cover every requested name (exact, or the wildcard of the parent; a wildcard does not cover the apex or a deeper name), also requires it to be valid now (not expired, not starting later than a five-minute tolerance), orders the rest behind it, and throws `CryptographicException` otherwise (the staged key keeps waiting); no staged row for the token is `StagedKeyMismatchException`, including after a replacement or delete. A certificate counts as the issuer of the one before only if the names link up, the key identifiers agree where both carry them, the issuer is a CA and its key verifies the signature (ECDSA or RSA PKCS#1 v1.5 with SHA-2); strays, same-name impostors, intermediates expired now and the root are dropped. Imports assemble the chain the same way.
- **Vault-signed certificates.** SAN (critical when the subject is empty), serverAuth EKU, key usage (`digitalSignature`, plus `keyEncipherment` for RSA), SKI, AKI (the root's SKI for a leaf), CA:false; serials are 126 random bits (the top two bits of 128 are fixed so the integer is positive and needs no sign byte); validity starts five minutes early. The root has CA:true with path length 0, `keyCertSign`/`cRLSign`, and the name `Paduraksa Local CA (<8 hex>)`; a leaf's validity is capped at the root's remaining validity and, for local-CA leaves and self-signed certificates, silently at 825 days (what Apple's trust store accepts); the root is not capped. The root has no name constraints and path length 0; name constraints (limiting it to the user's own domains) are deferred. The root is never served (`LoadForServingAsync` of its ID is `null`), cannot be replaced or staged over, and `EnsureLocalCaAsync` returns the existing one regardless of the ID it is given.
- **Contexts.** `CertificateContexts` implements both egresses over one cache of `SslStreamCertificateContext` (offline chain) per certificate: a load on a miss takes the vault's gate, writers invalidate inside it, so a context built from a replaced row can never be cached afterwards; the vault never disposes what it handed out. The cache is per process: a second process writing the same database would not invalidate it (the proxy's vault is the only writer; the KEK-rotating CLI does not change certificates). **Seals check the key.** Every operation that seals (certificate keys, staged keys, secrets, account keys) begins a transaction and re-reads the database's KEK check value first, refusing when it is not this process's KEK: a `rotate-kek` run while the service serves cannot make it seal under the old key (a rotation committing after the check makes the write fail). **Staged keys** are sealed to `{certificateId}/{stagedKeyId}` and a digest of their names, and a staging deletes staged keys older than 30 days (abandoned orders). A start whose generated `master.key` does not match the database names `master.key.old` or `master.key.new` when that one does (an interrupted rotation). `EnsureLocalCaAsync` for an ID other than the root's throws `LocalCaExistsException` carrying the real ID and info.
- **Import.** The upload is read into one pinned buffer (at most 1 MiB, stops reading at the cap), PEM key blocks are decoded from bytes (never through a string) and PFX is read under `CertificateImport.Limits` (32 certificates, one key, 600k iteration limits). Wrong password versus unreadable is told by the outer structure (ENCRYPTED PRIVATE KEY or PFX outer sequence parses: wrong password; otherwise unreadable), because the Pkcs12 and PKCS#8 info types are not in the shared framework. Contract addition: `CertificateImportFailure.NoUsableName` (a leaf with no DNS or IP SAN is refused before anything is stored, since nothing could ever select it).

**As built (M5): the Data Protection key ring.** `IDataProtectionKeyStore` (`Paduraksa.Core/Vault`) backs the admin app's `Microsoft.AspNetCore.DataProtection.Repositories.IXmlRepository`: `ReadAllAsync` returns every element, `StoreAsync` seals one element under its friendly name, and that is the whole surface (the optional `IDeletableXmlRepository` is not implemented, so a retired key stays in the ring until it expires). Each element is a row in the vault's own `DataProtectionKeys` table, sealed by the envelope cipher under the purpose `data-protection-key\n<friendly name>` with its typed `DataProtectionKeyId` and version in the AAD, inside the KEK-check sealing transaction, so editing the name or moving the ciphertext fails to open it. `vault rotate-kek` re-wraps the table (counted with the keys), and a restore keeps the ring because it is inside `vault.db`. A row that fails to open is logged at Error and skipped, so one damaged element does not take the ring down. The element XML **is** key material, so `DataProtectionKey.KeyXml` is the **third sanctioned egress** (after Kestrel's and the upstream mTLS contexts): the admin's `VaultXmlRepository` is its only reader, and it hands each element straight back to Data Protection in-process; `DataProtectionKey`'s printing hides it. No `IXmlEncryptor` is registered - the vault already encrypts at rest, so a second layer would only wrap ciphertext in ciphertext and need a key ring of its own to protect this one - and no file-system repository is created (`KeyManagementOptions.XmlRepository` is set to the vault's); the framework's "No XML encryptor configured" warning is filtered from the log. The ring is **admin only**: the dashboard's antiforgery and circuit state need it to survive a restart, while the public proxy gets YARP's session-affinity key from an in-memory `EphemeralDataProtectionProvider` (the affinity cookie is a destination ID, not a secret) and never reads or writes the vault; its Data Protection key-ring warm-up hosted service is removed so no key is ever created. The admin session cookie itself is Paduraksa's own random value, not Data Protection. The core host resolves no protector. The adapter and the `AddPaduraksaDataProtection` extension live in `Paduraksa.Admin.DataProtection`.

**Why the handler factory returns the whole transport.** A caller-supplied inner handler would see every request header, including the credential; a returned `DelegatingHandler` would let the caller swap its `InnerHandler` until the first send; and a response's `RequestMessage` would carry the injected header back. So the factory returns a sealed `internal` vault handler over a `SocketsHttpHandler` the vault builds itself (no automatic redirects, https only, timeouts, DNS refresh and proxy from `SecretHttpTransportOptions`), adds the credential to a **clone** of the request and sets `response.RequestMessage` back to the caller's original. It refuses non-https requests, hosts outside the allowlist and secrets that are not `DnsApiToken`, on every request. It never follows a redirect: providers handle 3xx themselves, and a redirect to another host fails the host check, so it never carries the credential. Tests substitute the transport through an internal seam in Vault, never through Core.

The `ISecretHttpHandlerFactory` pattern is the key trick. A DNS-provider client in `Paduraksa.Acme` builds an `HttpClient` over a vault-owned handler. The Cloudflare API token is added to the outgoing request *inside* the vault assembly and never exists as a value in Acme code. RFC2136 TSIG gets the same treatment through `IMacKey`.

### 8.3 At-rest encryption
- **Envelope encryption.** Each secret has its own random DEK (AES-256-GCM). DEKs are wrapped by the **KEK**. The AAD is `secretId || kind || version`, which stops anyone swapping ciphertexts between rows.
- **KEK source** in priority order: `PADURAKSA_MASTER_KEY_FILE` (Docker secrets / systemd `LoadCredential`), `PADURAKSA_MASTER_KEY` env, then auto-generated `data/master.key` (0600). The dashboard warns when the KEK sits in the same directory as `vault.db`.
- `paduraksa vault rotate-kek --new-key-file <path|->` re-wraps the DEKs (as built: the new key is read from a file or stdin, never argv; with the generated `master.key` the command stores the new key itself (old file kept as `master.key.old`, new one written through `master.key.new`, all 0600 and flushed with the directory, the old file put back if the rotation fails; standard input that is a terminal is refused and a group-readable key file is warned about); with a key file or the environment as the source the new key must come from a file the operator keeps).
- Plaintext buffers are pinned and zeroed (`CryptographicOperations.ZeroMemory`) after use, best effort.
- **Export.** Config export excludes secrets. An explicit "full backup" produces an archive with `vault.db` encrypted under a user passphrase (Argon2id-derived), and it is audited.
- **As built (M5): the Data Protection key ring** is one more sealed table (`DataProtectionKeys`), so it follows every rule above: its DEKs are re-wrapped by `vault rotate-kek`, its rows are protected by `secure_delete` and the WAL checkpoint, and it is covered by a backup of `vault.db` without any extra step.
- **As built (M3 vault core).** Format 1 of a sealed value is one BLOB: format byte, KEK ID (8 bytes), wrap nonce, DEK wrapped with AES-256-GCM (AES-KW does not exist in .NET, and GCM lets the wrap carry the AAD), data nonce, ciphertext, tag. The AAD of both operations is `domain || format || (KEK ID) || len(id) || id || len(purpose) || purpose || version`, with ID the typed-ID string (`sec_...`, `acct_...`) and the purpose carrying what decides how the value may be used: a secret's kind, MAC algorithm and allowed hosts, an account key's JWS algorithm. Editing that metadata in `vault.db` therefore makes the value fail to open (a change of hosts is a replace, which seals again). The KEK is base64 of 32 bytes from all three sources, and never becomes a string inside the vault when written; a source that is set but unusable is an error, never a fall-through. `master.key` is created exclusively with mode 0600 and never overwritten, and a new one is not generated if `vault.db` already holds data. An existing generated `master.key` readable by other users is refused (group access warns), judged on the open handle; an explicit key file is only warned about, since Docker secrets are mounted 0444. `vault.db` stores an HMAC check value of the KEK, compared at startup (`IVaultLifecycle.InitializeAsync`, which also reports whether the KEK sits beside the database), and runs with `secure_delete`. The previous value of a MAC secret verifies for 10 minutes after a replacement, then is deleted; `Sign` and `Verify` use cached key material and never wait for a rotation. **KEK rotation** (`IVaultKekRotation`) re-wraps every DEK in one transaction and checkpoints the write-ahead log, so the old wraps are overwritten; it re-wraps only, it does not re-key the data, so a copy of the old database plus the old KEK still opens that copy (to cut that off, replace the secrets). The order is the caller's: store the new KEK durably at its source, rotate, then retire the old one; the vault never stores the new KEK itself, and a crash with the new KEK stored nowhere after the commit would lose the vault. The authenticating handler allows only port 443 unless an allowed-host entry names the port (`host:8443`, in both the secret's and the caller's list), and it refuses a request whose `Host` header differs from its URL (domain fronting) and never copies it. Vault tests live in `Paduraksa.Tests.Vault`, a key-material boundary project.
- **Future hardening:** the capability interfaces are the seam for moving the vault into a separate process (gRPC over a Unix socket with peer credentials) without changing any callers.

## 9. Certificates & ACME

- **Own ACME client (RFC 8555)** in `Paduraksa.Acme`, about 1.5k LOC. We write our own instead of using Certes/ACMESharp because the account key must stay in the vault (`IJwsSigner`), and we want first-class **ARI (RFC 9773)** and **ACME profiles** (e.g. Let's Encrypt `shortlived`).
- **Challenges:** HTTP-01 (served by the public app's gate from an in-memory store). DNS-01 (provider plugins + propagation check by querying authoritative NS directly). TLS-ALPN-01 later.
- **DNS providers (v1):** Cloudflare, deSEC, Hetzner, DigitalOcean, Porkbun, DuckDNS, Route53, RFC2136, acme-dns, plus "manual" (show the TXT record and wait for confirmation) and a webhook provider. Interface: `CreateTxtAsync / DeleteTxtAsync / ValidateCredentialsAsync`. Every provider needs a **"Test credentials"** button in the UI.
- **CAs:** Let's Encrypt (prod/staging), ZeroSSL (EAB), Google Trust Services (EAB), Buypass, custom directory URL.
- **Account key rollover (RFC 8555 §7.3.5) is deferred past v1.** Recovery from a lost or compromised account key is a new account. The shape when it comes is additive on `IJwsSigner`: `StageAccountKeyAsync` (generate the new key, return its public JWK), `SignWithStagedAsync` (sign the inner `keyChange` JWS with it) and `CommitStagedAccountKeyAsync` (swap it in once the CA accepted the change). Nothing existing changes.
- **Renewal:** a background scheduler uses the ARI window if offered, otherwise renews at ⅓ of lifetime remaining, with jitter, exponential backoff and rate-limit awareness. On success the snapshot is recompiled and published (zero-downtime cert swap). On failure: notification + dashboard banner.
- **Auto-matching:** hosts with `CertificateBinding = Auto` get the most specific valid cert covering their names (exact beats wildcard). The dashboard flags hosts without coverage and offers "Issue cert for these names".
- **Other sources:** uploaded PEM/PFX (straight to the vault through the API's streaming endpoint, so the dashboard upload goes to that endpoint rather than through the Blazor circuit). Self-signed. **Local CA**: an internal root generated in the vault, issuing leafs for LAN-only hosts, with the root cert downloadable for installing as trusted.
- **Serving:** `SslStreamCertificateContext.Create(cert, chain, offline: true)` is prebuilt per snapshot, so no chain building happens during a handshake. **OCSP stapling is out of scope for v1.** Let's Encrypt dropped OCSP in 2025, and we don't want to promise cross-platform server-side stapling behaviour.
- **Expiry monitoring** covers every certificate, not just ACME ones. Uploaded and self-signed certs have no renewal path, so they get the same 30/14/7/1-day notifications and a dashboard badge. Local-CA leaves can be re-issued in one click (or automatically).

### 9.1 As planned for M3

Storage and compile-time decisions for certificates (decided before M3 work started):

- **Certificates, ACME accounts and DNS providers are not part of the config document.** They are operational resources in the config database (`Certificates`, `AcmeAccounts`, `AcmeOrders`, `DnsProviders`): metadata, the public chain and renewal state. Secrets appear only as `SecretId` references into the vault (§5.1, §8). Application services change them and audit every change; they do not create config revisions. Config export (§11.5) carries certificate metadata only.
- **The document references certificates only by binding:** Auto, Specific (`CertificateId`) or None. The compiler resolves bindings against the **certificate inventory** (the valid certificates and the names they cover), passed in alongside the document. Auto picks the most specific valid certificate covering the host's names: an exact name beats a wildcard, then the latest `NotAfter` wins.
- **A certificate change (issued, renewed, uploaded or deleted) recompiles the latest revision with the new inventory and publishes it**, without creating a revision. Deleting a certificate that a Specific binding uses is refused.
- **Replacing a certificate keeps its ID and is atomic.** Renewal, re-issue, a new upload and a new self-signed certificate on an existing `CertificateId` swap key and chain together in one vault transaction, so Specific bindings survive. ACME and manual CSR flows stage the new key first: `CreateKeyAndCsrAsync` returns a `StagedKeyId` that `AttachChainAsync` must present, so an overlapping second staging cannot silently take the first one's place (it fails with a documented exception instead).
- **The local CA root is a normal certificate.** `EnsureLocalCaAsync(CertificateId, ...)` creates it under a caller-chosen ID, so it has a Certificates row, expiry monitoring and a downloadable public chain like any other. Rotating or deleting the CA root is later work (with a plan for leaves issued under the old root); **nothing renews it yet** either, so its last 90 days shorten every leaf it issues (the admin listener's own included, §3), and that is the open item §3 refers to.
- **DNS credentials carry their own destinations.** The allowed hosts of a DNS token are metadata the admin sets when creating the DNS provider, stored with the secret (`SecretOptions.AllowedHosts`); the vault's authenticating handler uses their intersection with the provider code's own list, speaks only https, never follows redirects, and is the whole transport (§8.2).
- **Shared EF/SQLite infrastructure lives in `Paduraksa.Storage`** (§1): typed-ID conventions and converters, SQLite pragmas and the connection-string builder, the UTC timestamp converter. Vault may reference only Core and Storage, so it gets these without seeing any config entity.

### 9.2 As built: the certificate inventory (M3)

- **Storage.** `Certificates` (one row per `CertificateId`: source `acme`/`uploaded`/`self_signed`/`local_ca`/`local_ca_root`, status `pending`/`active`/`failed` with a message, subject, issuer, serial, AKI, SHA-256 fingerprint, key algorithm label, `NotBefore`/`NotAfter`, chain issuers, the **public** chain PEM, label, notes, created/updated) and `CertificateNames` (one normalised row per SAN, `NOCASE`, indexed). Expiry is not a status: it follows from `NotAfter` and the clock. Added as a new migration (`Certificates`), not a regenerated `Initial`, so a development database upgrades and parallel branches don't collide. No private key column exists; host bindings reference a certificate by ID with no foreign key (the document that names it is a revision, not a row).
- **`CertificateService`** (Application, DTOs in `Contracts.Certificates`): `RegisterAsync` (add, or replace the metadata under the same ID: a renewal), `RegisterPendingAsync`, `SetStatusAsync`, `UpdateDetailsAsync`, `DeleteAsync`, `ListAsync` (by source, status, or "covers this name"), `GetAsync` (with the chain). It never calls the vault: the vault flows call it after they created the key and chain. Every change is audited in its own transaction (`certificate.add`, `certificate.update`, `certificate.delete`; refusals too), creates **no revision**, and, when it affects serving (validity, names, chain, status), recompiles the latest revision with the new inventory and publishes it through the config writer (`ConfigService.ApplyCertificateChangeAsync`), so publishes stay ordered. Deleting a certificate that a Specific binding or the default certificate uses is refused with the paths of the referencing hosts. Names that are no DNS name, wildcard or IP address are dropped; none left is invalid.
- **Preload and the inventory.** Before each compile `CertificateInventoryLoader` reads the metadata (plus `IBuiltInCertificates`), judges each certificate against `TimeProvider` (active and inside its validity period), works out which valid certificates the document can choose (the named default, Specific bindings, the best match per name of every enabled Auto host), loads exactly those through `IServerCertificateSource`, and hands the compiler an immutable `CertificateInventory` whose resolver covers the loaded ones. A certificate the source can't load (null or an exception) is left out and the selection runs again, so Auto falls to the next best certificate. Contexts are used as the source returns them: an unchanged certificate keeps its instance, so the proxy's certificate table keeps one options object per certificate, and a renewal (a new instance) takes effect with the next publish. The inventory is a compile input, never mutated.
- **Selection is per name.** The proxy's certificate table maps names to certificates, so each DNS name of a host gets its own best certificate (`HostSpec.NameCertificates`), not one certificate for the whole host. A certificate covers a name when it lists it, or lists the wildcard of its parent (`*.example.com` covers `www.example.com`, not `example.com` or `a.b.example.com`); a wildcard host name is covered by the same wildcard. The best match is exact over wildcard, then the latest `NotAfter`, then the latest `NotBefore`, then the smallest ID. IP names never reach the table and ride the default certificate. Specific gives every name of the host that certificate (a certificate that doesn't cover them is a warning).
- **Degraded, never failed.** A name no valid certificate covers gets no certificate of its own: it is served with the default certificate, or rejected when there is none, and the compile reports `certificate.auto.noCoverage` (a `ConfigWarning` on the compilation, `ConfigService.Warnings` and the command result). A Specific binding, or a named default, whose certificate is missing, expired, pending, failed or without a key degrades the same way (`certificate.specific.unusable`, `certificate.default.unusable`), at startup, for the last-known-good fallback and for republishes: one bad certificate never fails the whole config, and an unreadable certificate table gives an inventory of the built-in certificates only. A **command** may not introduce such a binding (a new or changed Specific binding, or a changed default, naming an unusable certificate is `host.certificate.unusable` / `settings.defaultCertificate.unusable`, also in dry runs), but it is not blocked by a binding that went bad since. A rollback and the system's restore after a lost database are exempt: they put back a config that was accepted once, and degrade with warnings like startup does (the inventory may be gone with the database).
- **The placeholder.** (A year of validity: it is dev-only and new in every process, so only a process that runs for a year outlives it, and a restart replaces it.) `PlaceholderCertificates` is a source and a built-in inventory entry for the in-memory certificate under a well-known stable ID, and the inventory's fallback default. As built (vault certificates), it is composed **after** the vault (`CompositeServerCertificateSource`: a certificate the vault holds is never shadowed) and wired in at all only when `Paduraksa:Development:PlaceholderCertificate` is on (default: Debug builds yes, release builds no, §3); off, the source falls back to nothing, there is no built-in entry, and a document that still names the ID degrades like any missing certificate.
- **Validity follows the clock.** A certificate counts as valid from five minutes before its `NotBefore` (one named tolerance, for clock skew) until a second after its `NotAfter`. The inventory reports the earliest such boundary still ahead (`NextBoundary`, carried on the compilation as `ValidityChangesAt`); when a snapshot goes live the config service arms one `TimeProvider` timer for it (replaced by every newer live snapshot, cancelled on dispose), and when it fires it republishes the live config under the writer lock, coalesced with other publishes. So expiry and activation need no other trigger. A renewal under the same ID whose `NotBefore` is in the future leaves the names uncovered (with a warning) until that boundary, because the one row now describes the new certificate.
- **Republishing never publishes the empty config.** A certificate change or a validity republish compiles the database's latest revision, or, when the start is degraded on the last-known-good file or the database has no revision (it was lost), the last-known-good document. Without either it publishes nothing and logs why. A last-known-good republish doesn't end a degraded start. The compile happens inside the change's transaction, before the commit; after the commit nothing can fail the call.
- **After a database loss** the certificate rows are gone while the vault still holds the keys. The vault re-describes what it holds (`ICertificateCatalog`: `ListAsync`/`DescribeAsync` return the ID, whether it is the local CA root and the `CertificateInfo` of the stored chain; public data, read from the chain stored beside the sealed key, so no key is opened and no gate is taken; a row whose chain can't be read is left out and logged, and the query never names the sealed column, which a test pins). `CertificateRecovery` (Application) registers every certificate the vault holds that the inventory has no row for, through `CertificateService.RegisterRecoveredAsync`, as the system (audited; registrations are quiet, and the startup step queues one publish afterwards, so restored Specific bindings serve again). **Register-if-absent under the writer's lock:** per certificate, right before registering, the row's absence and the audit trail are checked inside the config writer's lock, so a registration racing with this (a vault-first upload) is never overwritten and an existing row, its label included, is never changed. **The source is not known**, so it is inferred from public facts and never guessed towards more capability: the root is `local_ca_root`; a certificate whose **signature verifies under that root's public key** (a custom-root `X509Chain`, time and revocation not judged; a matching issuer name alone is not enough) is `local_ca`; everything else is `uploaded` (a lost self-signed one too, since it cannot be told from an uploaded self-signed one, and an upload is never replaced by a re-issue; a lost ACME one too: its order, account and schedule were in the lost database, so it is not renewed until requested again). Each recovered row has the label `Recovered from the vault`. **A deleted certificate is not resurrected:** deleting removes the row (audited as `certificate.delete`) and then the key; if the key's deletion failed the vault still holds it while the database is intact, so a successful `certificate.delete` on record for the ID means "finish the deletion" (`ICertificateIssuance.DeleteAsync`, retried at the next start if it fails) instead of registering; the same trail covers a creation that was rolled back (its pending row was deleted and audited). A key with no such trail (a registration that was refused, an upload interrupted between the vault and the row) is registered, visible and deletable, and a lost database loses the trail with it, so nothing is treated as deleted then. One window remains: an upload that reached the vault but has not registered when this runs is registered as recovered and its own registration then replaces the metadata (an upload without a label keeps the recovered one). It runs once per start, in the core host (`CertificateRecoveryStartup`), as an **awaited start step after the config store and before the web apps**: registrations are quiet (no republish per certificate), then one publish is queued, so the first snapshot the listeners serve already includes the recovered certificates. The step is bounded by `Paduraksa:Certificates:RecoveryStartupTimeout` (10 s; 1 s to 5 min); past it the run continues in the background and the start goes on. A stop is checked between certificates, and registrations and key deletions run with `CancellationToken.None`, so an abort never cancels a transaction partway through (and EF never logs it at Error). `SharedServices.RecoveryCompletion` completes when the run has finished, which tests await instead of sleeping. It skips a store that does not accept changes, never stops the process, logs one summary line and leaves certificates that have a row alone whatever the row says.
- **The vault flows** (`CertificateOperations`, DTOs in `Contracts.Certificates`; Application): upload (optionally over an existing uploaded certificate), self-signed, local CA root, local-CA leaf, re-issue (self-signed and local-CA only, same ID and names) and delete. Each is one authorizer call (`ICertificateOperationAuthorizer`, allow-all until M4), the vault call and the `CertificateService` registration (so audit and republish are the service's). **Ordering** decides what a failure leaves: a new certificate whose names are known (self-signed, leaf, root) is registered *pending* first (validates names, visible, never served), then the vault creates key and chain, then the same row is registered active; a failed vault call or a refused registration deletes the pending row and the key again (not cancellable), and a crash between leaves a visible pending row, never a hidden key. A new upload learns its names from the vault, so it goes vault first and is rolled back (key deleted) if the registration is refused; a key with no row is never loaded. Replacing an existing ID swaps in the vault first (it cannot be undone) and then updates the row; if that fails the result says so, it is logged, and repeating the operation repairs it. Delete asks the inventory first, which refuses (nothing touched in the vault) while a Specific binding or the default certificate uses it, then deletes the key; a failed key deletion is a warning in the result (the certificate is already gone from the inventory, the key unreachable). Deleting the local CA root is refused while local-CA leaves exist; a delete with no row still removes an orphaned key. The root has no names, so `RegisterAsync`/`RegisterPendingAsync` accept an empty name list for `CertificateSource.LocalCaRoot`. The label (and what the inventory would refuse about the request) is checked before the vault is called, so a replacement is never reported invalid after the vault took it. Only an *active* root row counts as the local CA: a root row a crash left pending is completed under its own ID, and when the vault holds the root under another ID (the inventory was lost) it is recorded under that ID (`LocalCaExistsException`), which also repairs the database-loss case for the root. The key deletions after a commit and the rollbacks run with `CancellationToken.None`, and a failed creation always deletes the key (idempotent), so a cancelled request leaves no orphan. Request DTOs carry `KeySpec` as its stable name (`ecdsa-p256`, `rsa-2048`, ...).
- **Built-in IDs** (`IBuiltInCertificates`) can't be registered in the table: the built-in would silently win.
- **The process's own admin certificate** (`AdminCertificate.Id`, PLAN §3) is an ordinary `local_ca` row with a stable ID and the label `Admin (internal CA)`, plus `certificate.managed`: deleting it, re-issuing it by hand and binding it (Specific or as the default) are all refused, and the inventory loader leaves it out of what the compiler sees. `CertificateService.RegisterQuietlyAsync` is `RegisterAsync` without the republish, which is what the core host's `AdminCertificateService` uses: it adopts the vault's existing leaf (via `ICertificateCatalog.DescribeAsync`) instead of issuing a new one when the row is lost - and only when that leaf carries exactly the names the run would ask for, or the next run would re-issue it anyway - so a database loss with unchanged names leaves the served fingerprint alone. When it is the other way round (the row is there and the vault's key is gone, `vault.db` deleted or restored from an older copy) the service retires a stale root as `failed`, makes a new root and issues a new leaf, so the admin port comes back with no operator step. `CertificateRecovery` skips the ID entirely: the service owns it, so the two writers cannot race over one fixed ID. A rollback of the admin leaf still removes its row - which writes a `certificate.delete` audit event (a refused one is `invalid`, a successful one `success`) - but it never deletes the vault's key: the ID is fixed, so the pair the vault holds may be the only servable one, and the next run adopts it. The local CA root is adopted the same way (registered under `CertificateRecovery.Label`), and `local_ca.inUse` tells the user the root is in use rather than telling them to delete the admin leaf, which they can't. Nothing renews the root yet: its lifetime caps every leaf it issues, so the last 90 days of the root shorten each re-issued admin leaf (root rotation is still open in §9.1).

### 9.3 As built: ACME issuance and renewal (M3)

- **Storage** (migration `AcmeIssuance`). `AcmeAccounts` (directory URL, contacts, status `active`/`deactivated`, account URL, key algorithm, EAB key id (`EabKid`, the CA's identifier, not a typed ID) and `EabSecretId`, ToS agreed, label), `DnsProviders` (kind `cloudflare`/`desec`, label, `CredentialSecretId`) and `AcmeOrders`: **one row per certificate** (unique `CertificateId`, cascade with the certificate; account and provider are `Restrict`; DNS-01 requires a provider by a check constraint), reused by every issuance and renewal, so "one issuance per certificate" is a property of the table. Enums by stable name with check constraints (a new DNS kind is an enum member plus a migration). The `Certificates` row stays the serving metadata (`source = acme`). Secrets appear only as `SecretId`; the staged key is a token, the stored CSR is public.
- **Services** (Application, DTOs in `Contracts.Issuance`): `AcmeAccountService` (create: `IJwsSigner.CreateAccountKeyAsync` → `newAccount`, EAB through `IMacKeySource`; a refused registration deletes the key again and records nothing; deactivate is final, refused while certificates use the account, and deletes the vault key; list/get), `DnsProviderService` (create over an existing `DnsApiToken` secret, delete refused while in use, "Test credentials"), `AcmeIssuanceService` (below), `AcmeRenewalScheduler` (hosted service), `AddPaduraksaIssuance` for the container. Accounts and providers are audited through `ConfigService.ApplyOperationalChangeAsync`: the config writer's lock and transaction, so every audit event stays on the one hash chain, with no revision and no publish. Wired into the process: see **Server wiring** below.
- **Orchestrator state machine.** `RequestCertificateAsync` validates (names normalised like SANs; HTTP-01 refuses wildcards, DNS-01 refuses IPs and needs a provider; the account must be active), registers a pending certificate (`CertificateService.RegisterPendingAsync`), inserts the order row, and runs. `RenewAsync` is the one entry for "do the next step": a `valid` row starts a new order (decided from the row read under the certificate's guard) (the CA is told `replaces` = the ARI ID of the certificate being renewed, and only `alreadyReplaced`, or a bare `serverInternal` 500 with no `Retry-After`, repeats the order without that hint (a 503, 408, bad nonce, rate limit or any `Retry-After` keeps the normal backoff, so the CA's timing, its load and the ARI renewals' rate-limit exemption are respected; the retry is logged at Warning with the certificate ID and problem type only)), an unfinished or `failed` row continues. A run **follows the CA's order status**: read the stored order (an order that is `invalid` or `expired`, or that the CA refuses to show with a permanent problem such as 404, is forgotten; `accountDoesNotExist` is not: it marks the account deactivated), else `newOrder` (URL saved, row `ordered`); `pending` → fulfil every pending authorization (publish, respond, wait, always clean up); `ready` → `CreateKeyAndCsrAsync`, save the staged-key token and the CSR (row `finalizing`) **before** `finalize`; `processing` → wait; `valid` → download (preferred chain by issuer CN), `AttachChainAsync`, then **save the returned public `CertificateInfo` on the row (`AttachedInfo`)** and finish with `CancellationToken.None`: `CertificateService.RegisterAsync` (active; existing republish; retried a few times if the store is busy), plan the renewal, row `valid` (`AttachedInfo` cleared), audit `acme.order.issued`. A run does not start when the config store is degraded (nothing could be recorded). Row statuses: `pending`, `ordered`, `finalizing`, `valid`, `failed`.
- **Resume.** Because the CA's state decides, a restart (or a retry) continues the same order where it stands: finalize is submitted from the saved CSR, a `processing` or `valid` order is attached to the saved staged key, a challenge already `processing` is only waited for. Cancellation (shutdown) leaves the row as it was; every other failure is recorded. A row with `AttachedInfo` skips the download and attach and only registers, so cancellation or a refused registration after the attach cannot strand the new certificate. The hard-crash gap (the process dying between the vault's attach returning and `AttachedInfo` being saved, which left the vault serving the new certificate under the old metadata with a spent staged key) is closed by `ICertificateCatalog` (§9.2): when attaching meets `StagedKeyMismatchException`, the service asks the vault to describe the certificate and, if the leaf it holds is this order's downloaded leaf (the described SHA-256 fingerprint equals the hash of the leaf's DER), takes its `CertificateInfo` as the attach result (a warning is logged) and goes on to register; another leaf is a real mismatch and fails as before.
- **Failures** are classified by `AcmeFailureKind` (and DNS provider/own failures), stored on the row (message, `Attempts`, `LastAttemptAt`, `RetryAt`) and audited (`acme.order.failed`). A certificate that was never issued (or has expired) becomes `failed` with the message; a renewal that fails while the old certificate is valid leaves it `active` and serving. An order that cannot be continued (invalid or deactivated authorization, invalid order, spent staged key, CSR refused) is dropped so the next attempt makes a new one; anything else resumes (a finalize that races with another and meets `orderNotReady` on a processing order continues with it). An account the CA no longer knows is marked deactivated. Messages are sanitised and cut to 1024 characters.
- **HTTP-01.** `AcmeChallengeStore` (Proxy; `IAcmeChallengeStore` in Core is the publish side): in memory, at most 1024 tokens, each counted by its holders (two issuances sharing a pending authorization keep it answered until both removed it), entries validated (base64url token, printable-ASCII key authorization) and stored as a ready `PrecomputedResponse`. The gate (`GateMiddleware`, optional constructor argument, registered once in `SharedServices`) answers **plain-HTTP GET/HEAD** `/.well-known/acme-challenge/{token}` for an exactly matching published token with 200 `text/plain` before host lookup and every policy, 0 B on hit and miss. Any other request under the path (unknown token, another method, HTTPS) falls through to the normal pipeline rather than a blanket 404, so an upstream that runs its own ACME client keeps serving its own challenges. A hit is never logged.
- **DNS-01 seam.** `IDnsProvider` (`CreateTxtAsync`/`DeleteTxtAsync`/`ValidateCredentialsAsync`, idempotent, `DnsProviderException` says transient or not) and `IDnsProviderFactory` live in `Paduraksa.Acme.Dns`. A wildcard and its base name publish two TXT records at one name; all are created, the orchestrator waits (§9.4: the authoritative-NS propagation check, or `DnsPropagationDelay`, 30 s, as the fallback), responds, and deletes the records afterwards even on failure. The Cloudflare and deSEC providers are §9.4.
- **Scheduler timing** (`RenewalSchedule` is pure arithmetic, `TimeProvider` and an injectable random source drive the rest). The row says what is due: **`NextRenewalAt`**: with an ARI window, a uniformly random point in it (never after `NotAfter`; a window in the past is due now); without, `NotAfter` - ⅓ of the lifetime, moved earlier by up to 10 % of that third (30 days of 90, 2 days of 6). An ARI pick is never later than that ⅓ rule (a window at the end of life must not become an outage). **`AriCheckAt`**: the response's `Retry-After` bounded to 15 min...24 h (6 h without); a recheck keeps the old pick if it is still inside the window, else picks again. **`RetryAt`** after a failure: exponential from the kind's base, ±20 % jitter that stays symmetric and never passes the cap (the doubling stops at cap/1.2): transient 5 min → 6 h, permanent 1 h → 24 h (a retry still happens: a DNS record may be added later), protocol violation 30 min → 24 h, rate limited 1 h → 7 d but never less than the CA's (or a DNS provider's 429) `Retry-After`; a transient failure with a `Retry-After` (a 5xx, say) is floored by it too, up to its cap. `RunOnceAsync` (every minute, after a start delay, one certificate at a time) lists the orders and calls `AcmeIssuanceService.RunDueAsync` for each, which **re-reads the row under the certificate's guard** and applies the due rules to that fresh row (the listing can be minutes old): unfinished order → resume; `failed` and `RetryAt` passed → retry; `valid` and `NextRenewalAt` passed → renew, else `AriCheckAt` passed → refresh ARI (also under the guard). Failures are logged and kept on the order and the certificate; notifications come with the channels (M7).
- **Server wiring** (`IssuanceStore`, composed in `SharedServices.Create` after the vault, the config store and the shared `AcmeChallengeStore`, which the public gate reads and the issuance service publishes to through `IAcmeChallengeStore`). `AddPaduraksaIssuance` runs in a container `SharedServices` owns, over the real vault (`IJwsSigner`, `IMacKeySource`, `ISecretStore`, `ICertificateIssuance`, `ICertificateCatalog`), the config store's context factory, `ConfigService` and `CertificateService`; the account, DNS provider and issuance services and the scheduler are shared instances (`SharedServices.AcmeAccounts`/`DnsProviders`/ `AcmeIssuance`/`AcmeScheduler`). **Options** are `Paduraksa:Acme` (`PaduraksaAcmeOptions`, validated at startup): `Enabled` (the scheduler; default on), `TrustedRootsFile`, `SchedulerStartDelay` (15 s; 0 to 1 h), `SchedulerPollInterval` (1 min; 1 s to 1 day), `DnsPropagationDelay` (30 s; 0 to 1 h); and `Paduraksa:Development:AcmeInsecureHttp` (off; `AcmeClientOptions.AllowInsecureHttp`, which admits `http://` only for **loopback hosts**, so any other host's `http://` URL is refused even with it on; a startup warning when on). The bounds keep a typo from becoming a delay `Task.Delay` cannot take, and the scheduler also clamps its pauses to a day and catches whatever a pause or a look trips over, so the loop never faults the host. **CA trust:** one transport for every ACME client of the process (`AcmeHttp.CreateHandler(roots)`: never follows redirects; the chain check also accepts a chain that ends at one of the roots in `TrustedRootsFile`, a PEM file of at most 1 MiB, relative paths against the content root; the system's trust is tried first, then the roots' with the chain valid now, the intermediates the server sent, the `serverAuth` extended key usage required and the name still matching; revocation is not checked for either kind, the transport's default). Every root must be a **self-signed CA certificate**: the file is read once, at startup, and an intermediate, a leaf or no certificate stops the process with the file named. The handler keeps copies, is owned by the shared services and disposed after the container holding the clients. **Scheduler lifecycle:** a hosted service of the core host only (`CoreHost`, when `Enabled`), registered after `VaultStartup`, `ConfigStartup` and `CertificateRecoveryStartup`, so the vault and the config store are up first; its first look waits `SchedulerStartDelay` and then `IProcessReadiness` (every listener bound), so an HTTP-01 validation never runs before the public listener can answer it. **On shutdown it is drained first**, before the public app stops (`PaduraksaHost.StopHostsAsync`): `AcmeRenewalScheduler.DrainAsync` starts no new look or certificate, lets the one in flight finish for up to 10 s (an HTTP-01 validation needs the public listener to answer), and then cancels what is left (a cancelled run leaves the order as it was and resumes at the next start); an idle scheduler stops at once. The core host's own stop then finds it finished. **DNS providers:** none are registered yet, so `IDnsProviderFactory` is absent and a DNS-01 request fails as "not supported"; the DNS provider registration (`AddPaduraksaDnsProviders`, with the Cloudflare/deSEC providers) goes in the `IssuanceStore` chain before `AddPaduraksaIssuance`. The DNS providers and the propagation check are registered there too (§9.4), so a DNS-01 request is no longer "not supported".
- **Tests.** The orchestrator, scheduler and services run in `Tests.Issuance` (its own project, because it alone lifts the key-material ban for its test code) on real SQLite and the real config writer against the ACME client's fake CA, a fake vault (`ICertificateIssuance` and `ICertificateCatalog` with staging rules; its reported fingerprint is the SHA-256 of the leaf's DER, as the vault's is) and a virtual clock; `CertificateRecoveryTests` there run recovery over real certificates (sources by signature, a same-name impostor, rows left alone, a deleted certificate's key deleted, a refused deletion). `Tests.Acme` has loopback-TLS tests of the trusted-roots handler (accepted: root plus intermediate; refused: name mismatch, expired leaf, another root, clientAuth-only leaf, missing intermediate, an intermediate as a root) and of the loopback-only plain-http rule. `Tests.Proxy` covers the gate; `Tests.Unit` the schedule arithmetic. `AcmePebbleTests` run the orchestrator against a real **Pebble** (Docker, `PEBBLE_VA_ALWAYS_VALID`, random ports, skipped when Docker or the image is unavailable; `PADURAKSA_PEBBLE=off` skips, `PADURAKSA_PEBBLE_DIRECTORY` uses a running one): real CSRs from a stand-in issuance, ARI by the computed certificate ID, `replaces`, IP and wildcard identifiers. **`PebbleIssuanceEndToEndTests`** (`Tests.Integration`) are M3's exit criterion with the real stack: a `PaduraksaHost` (real vault, config database, scheduler and public listener) against a **validating** Pebble (`PEBBLE_VA_ALWAYS_VALID=0`). *Topology:* Pebble (v2.10.1, pinned by digest, labelled with the test process's id so a killed run's leftovers are removed at the next one; not `--rm`, so a container that exits can be inspected and its logs reported) in Docker on the host's network (`--network host`), listening on loopback ports picked per test, with a config the test writes (`httpPort` = the process's public HTTP port, retry hints of one second); the test names resolve to 127.0.0.1 through the container's `/etc/hosts` (`--add-host`), so its validation authority fetches `http://name:port/.well-known/acme-challenge/token` from the **gate**. (The bridge network with `host-gateway` does not work behind a typical Linux host firewall, and Docker Desktop has no host network: the tests skip on non-Linux.) The process trusts Pebble through `Paduraksa:Acme:TrustedRootsFile` (its minica root, copied out of the image once per run). Cases: request via HTTP-01 and the proxy serves the Pebble-issued leaf for every name (TLS handshake); renewal keeps the `CertificateId` and the revision and the served certificate changes, with the ARI window recorded and the renewal scheduled inside it; a restarted process whose renewal came due while it was down renews it with its own scheduler; a failed validation leaves a failed row with a retry, a coverage warning and nothing served (the handshake is refused); without the root the directory is not trusted. `AcmeHostingTests` cover the scheduler's switch (`Enabled=false` hosts none) and drain, the pacing bounds, the trusted-roots file's refusals and the plain-http warning. A `pebble-challtestsrv` (DNS-01 against Pebble) is not used yet: DNS-01 against Pebble waits for the real DNS providers.

### 9.4 As built: DNS-01 providers and the propagation check (M3)

- **Credential path.** A provider (`Paduraksa.Acme.Dns`) is built from a `SecretId` and the vault's `ISecretHttpHandlerFactory`; each operation opens an `HttpClient` over `CreateAuthenticatingHandler(secretId, injection, transport)` and disposes it (so the pool never outlives the call). The token is never a value in Acme code; the provider declares its own host in the `SecretInjection` (`api.cloudflare.com` with `Bearer`; `desec.io` with `Authorization: Token`), which the vault intersects with the secret's `AllowedHosts`. A vault refusal (`InvalidOperationException`: host not allowed, secret gone) is a permanent `DnsProviderException`. `DnsApiClient` is the shared plumbing: bounded body (1 MiB), per-call timeout (30 s, on the system clock), `Retry-After` parsed, JSON by source-generated contexts (`CloudflareJsonContext`, `DesecJsonContext`). Messages hold the provider name, an HTTP status and the provider's own error text (control characters removed, cut to 200); never a header.
- **Failure classification.** 429, 5xx, timeouts and network errors are transient; other statuses, a body that is not the expected JSON, an oversized body and "no zone/domain for this name" are permanent. A 429 is also flagged `DnsProviderException.IsRateLimited`, which the orchestrator maps to `AcmeFailureKind.RateLimited` (1 h base, `Retry-After` as a floor); a 5xx with `Retry-After` stays transient with the hint as a floor. A 429 whose `Retry-After` is within `DnsProviderOptions.MaxInlineRetryAfter` (65 s, so deSEC's per-domain write limit is waited out) is waited out once inside the call; a longer one throws.
- **Cloudflare** (API v4, scoped token): zone found by `GET /zones?name=` for the name and each parent down to two labels (longest first; a token scoped to some zones just sees no others), cached per provider. Create first lists CNAME records at the name (found: permanent "CNAME delegation is not supported yet"), then the TXT records (paged, 100 per page; more than 20 pages is refused, never cut off), skips if the value is there, else `POST` with TTL 60; "identical record exists" (81058) counts as created. Delete lists, then `DELETE`s exactly the records whose content equals the value (quotes Cloudflare may add on output are ignored; a 404 is logged as "already gone"), so the wildcard's and the base name's values coexist. Validate: `GET /user/tokens/verify` (status must be `active`), then a zone read (`GET /zones?per_page=5`, the documented minimum): an account-owned token, which the user endpoint rejects, is judged by the zone read alone, and a token that reads no zone is invalid. DNS:Edit cannot be checked without writing, so a token that can read but not edit fails at the first create.
- **deSEC**: domain by `GET /domains/?owns_qname=` (the most specific the account owns; `subname` is the rest). RRsets are whole: `GET .../rrsets/{subname}/TXT/` (404 = none), add or remove values, write back the **full** `records` list. Writes are **batched per domain** because deSEC limits them (2/s, 15/min, 100/h, 300/day per domain): `IDnsProvider.CreateTxtBatchAsync`/`DeleteTxtBatchAsync` (default: one by one; Cloudflare uses the default) take the whole order's records, and deSEC sends at most one bulk `POST /rrsets/` (new sets) and one bulk `PATCH` (changed sets; `records: []` deletes) per domain. No `PUT` is sent (deSEC needs the whole resource there). A bulk `POST` that meets a set created meanwhile (400) re-reads and goes on as a `PATCH` once. A CNAME at the name is refused as with Cloudflare. Values are written quoted with `\\` and `"` escaped and compared unquoted (a multi-string record `"a" "b"` reads as `ab`). The TTL is at least the domain's `minimum_ttl` (3600 default) and never lowers an existing set's. There is no ETag, so two writers racing on one set could lose a value. Validate: one bounded `GET /domains/?owns_qname=` (an unlisted full domain list pages above 500 domains).
- **DNS client choice.** `System.Net.Dns` only does address lookups; .NET 10 has no NS/TXT query. A package (DnsClient.NET, Apache-2.0) was weighed and not taken: the check needs only A/AAAA/NS/TXT over UDP with TCP on truncation, pointed at chosen addresses, and a ~300-line codec (`DnsWire`, `DnsClient`, internal to Acme) keeps the dependency list and the parser's limits ours. Parsing is bounded: messages at most 65535 bytes, names at most 255 bytes and labels 63, compression pointers only backward into the message body and at most 32 followed, reserved label types and non-hostname bytes rejected, every length checked against the message and the record's RDLENGTH, at most 256 answers, authority and additional sections never read. Queries carry a random 16-bit ID (`RandomNumberGenerator`) and an EDNS0 OPT (1232 bytes); each uses its own connected socket, and a datagram whose ID, question name (case-insensitive), type or class do not match, or that does not parse, is ignored until the timeout. A FORMERR answer to the EDNS0 OPT record is retried once without it. Not done: 0x20 case randomisation and DNSSEC validation (the check informs a wait, not a trust decision).
- **Propagation check** (`IDnsPropagationCheck`, `AuthoritativeDnsPropagationCheck`): (1) NS records for the name and each parent (down to two labels) from a recursive resolver; (2) A and AAAA of each name server through the resolver; (3) every name server is asked directly for the TXT records at the name (RD off) until each returns every expected value (several values at one name all required, text strings joined) with the AA bit set and NOERROR/NXDOMAIN. A name server with several addresses is done when one address gives an authoritative answer. Rounds run in parallel across servers: the first at once, then the pause starts at 2 s and grows x1.5 to 15 s, until `Timeout` (5 min); a query times out at 3 s. A server with no authoritative answer for 3 rounds in a row is left out and not asked again (a limitation: a name server that is merely slow to start answering may then be stale for a CA that asks it); if none is left, or no zone or resolver is found, the outcome is `Unverifiable`. Resolvers are `DnsPropagationOptions.Resolvers`, else the DNS addresses of the system's network interfaces, else 1.1.1.1 and 8.8.8.8. Satisfaction is reset for a zone's servers when more records join it, so every record is asked for. Outcomes: `Propagated`, `TimedOut` (with `AnyServerHadRecords`) and `Unverifiable`. Settings are bindable through `DnsPropagationSettings` (`Paduraksa:Acme:DnsPropagation`: `Enabled`, `Timeout`, intervals, `Resolvers`).
- **Orchestrator.** `AcmeIssuanceService` takes an optional `IDnsPropagationCheck` and publishes an order's records in one `CreateTxtBatchAsync`. `Propagated` goes on to respond. `TimedOut` with at least one server holding a record goes on too (a warning is logged; the CA's verdict is the real one); `TimedOut` with **no** server holding any record fails the attempt as transient (cleanup runs, nothing is asked of the CA: a failed validation counts against its limits). `Unverifiable`, a check that throws, or no check waits `AcmeIssuanceOptions.DnsPropagationDelay` as before. Cleanup is one `DeleteTxtBatchAsync` on its own 3-minute real-time budget, retried up to three times on a transient failure (waiting the provider's `Retry-After`, up to 65 s), so a throttle does not leave records behind.
- **Registration.** `AddPaduraksaDnsProviders(DnsPropagationSettings? propagation = null)` (Application, `DnsProviderServiceCollectionExtensions`) registers `DnsProviderFactory` as the `IDnsProviderFactory` (`DnsProviderKind` picks Cloudflare or deSEC) and, if `Enabled`, the authoritative check as `IDnsPropagationCheck`; it needs `ISecretHttpHandlerFactory`, uses `DnsProviderOptions`, `DnsPropagationOptions`, `TimeProvider` and `ILoggerFactory` when registered, and keeps anything already registered. `AddPaduraksaIssuance` passes whatever `IDnsPropagationCheck` is registered to the orchestrator. Disabled keeps the fixed delay (a host that cannot send DNS to the zone's servers). The Server composes it in `IssuanceStore`: `AddPaduraksaDnsProviders(acme.DnsPropagation)` runs before `AddPaduraksaIssuance()` in the issuance container, over the vault's `ISecretHttpHandlerFactory`. **Options:** `Paduraksa:Acme:DnsPropagation` binds into `DnsPropagationSettings` (`Enabled` true, `Timeout` 5 min, `InitialInterval` 2 s, `MaxInterval` 15 s, `QueryTimeout` 3 s, `UnreachableRounds` 3, `Resolvers` empty = the system's); the validator refuses (and the process does not start) a timeout outside 1 s...1 h, intervals outside 0.1 s...10 min or a maximum below the initial, a query timeout outside 0.1...30 s, rounds outside 1...20, more than 8 resolvers or one that is not an IP address. `Paduraksa:Acme:DnsPropagationDelay` stays the fallback wait.
- **Not supported yet: CNAME delegation** (`_acme-challenge` CNAMEd to a zone elsewhere, the usual way to keep tokens off the main zone). Both providers refuse a name that is a CNAME with a permanent, explicit error. Later: follow the CNAME and publish and check at the target, with a provider configured for the target's zone.
- **Tests.** `Tests.Acme`: both providers against in-memory Cloudflare and deSEC APIs behind a fake of the vault's handler (https and host check, injection format; zone walk, two coexisting values, quoting, paging, 404, 429, error mapping, no token in messages or logs); the DNS codec (truncation at every length, 5000 randomly damaged messages, pointer loops and forward pointers, bad lengths) and client (wrong ID or question ignored, TCP on truncation, timeouts) against a fake UDP/TCP server; the propagation check against a fake resolver and two authoritative servers on 127.0.0.2 and 127.0.0.3 (skipped where those loopback addresses do not answer). `Tests.Issuance`: the orchestrator's use of the check and its fallbacks, the registration, and "Test credentials" through the real Cloudflare provider. Live Cloudflare and deSEC round trips (`LiveDnsProviderTests`) run only with `PADURAKSA_LIVE_CLOUDFLARE_TOKEN`/`_NAME` or `PADURAKSA_LIVE_DESEC_TOKEN`/`_NAME`. Most of these go through a fake of the vault's handler; `Tests.Vault` (`DnsProviderThroughVaultTests`) runs the Cloudflare provider over the vault's real authenticating handler (bearer token seen by the terminal; a secret whose allowed hosts lack `api.cloudflare.com` is refused permanently without the token in the message). `Tests.Integration` (`AcmeHostingTests`) checks that the providers are installed in the real host and that invalid `DnsPropagation` settings refuse the start. Not done: a Pebble DNS-01 end-to-end test (it needs pebble-challtestsrv as a second container and a test provider that writes to its HTTP API; the propagation check would also have to find its name servers there).

## 10. Authentication & authorization

There are two separate domains:

### 10.1 Admin auth (dashboard / API / MCP)
- Local users: password + **TOTP** + **passkeys** (WebAuthn). ASP.NET Core 10's passkey support ships inside **Identity**, which we don't use. M4 includes a short check of whether its WebAuthn primitives work standalone; otherwise we use **Fido2NetLib** (fido2-net-lib). Budget for the latter. Lockout and rate limiting on login. Session list with revoke.
- Roles: **Owner** (users, vault, everything), **Admin** (all config), **Operator** (hosts/certs, no users/secrets), **Viewer** (read-only), **Auditor** (audit log + read-only). Implemented as permission sets, so custom roles can be added later.
- API: Bearer `pdk_...` tokens with scopes and expiry. MCP uses the same tokens, read-only by default, with the MCP authorization spec (OAuth) considered later.
- **Pluggable providers:** `IAdminAuthProvider` with Local (v1), OIDC (authentik/Keycloak/Pocket-ID: claim → role mapping, JIT provisioning) and trusted-header (when the admin itself sits behind forward-auth).
- **Hard rule for trusted-header auth:** it's accepted **only** on connections from the internal proxy listener (§3.1), from loopback, or from an explicitly configured CIDR. It can't be enabled while the admin port is bound to a non-loopback address without that CIDR. Validation rejects the config, and the request path re-checks the peer address every time. Otherwise anyone on the LAN could spoof `X-authentik-username`. When forwarding to the admin, the public side strips any client-supplied copies of the trusted headers.
- Hardening: strict CSP, antiforgery, `SameSite=Strict` cookies, Data Protection keys in the vault, optional admin IP allowlist, every login/failure audited.
- **As built (M4).** The permission-based authorizers replace the allow-all ones (`AddPaduraksaIdentity` replaces `IConfigCommandAuthorizer` and `ICertificateOperationAuthorizer`, whichever order they are registered in): `config:write` for every config command, `certificates:write` for certificate operations. Services that change things outside the command pipeline ask up front, before any CA order, key or pending row exists, and answer with a distinct refusal that is audited as denied: `CertificateService` (`CertificateChangeStatus.Denied`, which `CertificateOperations` maps to `Forbidden`; its rollbacks run as the system so a refused or revoked caller cannot leave a pending row), `AcmeIssuanceService.RequestCertificateAsync` and `RenewAsync` (`certificates:write`, `IssuanceOutcome.Forbidden`), `AcmeAccountService` and `DnsProviderService` mutations (`providers:write`, `IssuanceChangeStatus.Denied`). While the config store is unavailable the check is skipped (the permissions live there, and the operation answers `Unavailable` and starts nothing). Refused identity *changes* are audited; refused reads (listing users, sessions, tokens) are not, since reads are not audited; the system and the CLI may do everything, and the allow-all ones remain for tests. Lockout, sessions and password settings live under `Paduraksa:Admin` (validated bounds: 2 to 100 attempts, 1 min to 24 h lockout, 5 min to 30 d sessions, idle at most the lifetime, 8 to 128 minimum length, 100 000 to 10 000 000 iterations). The HTTP surface is below. Not built: passkeys (M5), OIDC and trusted-header providers.

- **As built (M4): the admin pipeline** (`Paduraksa.Admin`: `AddPaduraksaAdminAuth`, `UsePaduraksaAdminAuth`, `MapPaduraksaIdentityApi`; `AdminApp` only calls them). Order: the loopback listener's host check, security headers, the setup gate, routing, request body limit, CSRF check, authentication, then the endpoints. Any endpoint can opt in to the mechanisms with public metadata: `.AllowAnonymousAdmin()` (no credentials needed; a stale cookie ignored), `.WithAdminBodyLimit(bytes)`, `.AcceptsAdminContentTypes(...)`, `.RequireAuthenticated()`, `.RequirePermission(...)`. Authentication covers `/api/` and only ever *sets* the `AdminCaller`; a request that already has one is left alone.
- **Credentials.** Session cookie `__Host-paduraksa-session` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`; the value is the session secret, checked by `SessionService` on every request) or `Authorization: Bearer pdk_...` (`ApiTokenService`, also checked every request, so a revoked token or session dies at once). A credential that is presented and wrong is a 401, never an anonymous request: a bad token, an unknown or expired cookie (which is also cleared), a non-Bearer `Authorization`, two `Authorization` headers, the cookie twice, or a cookie *and* a token together. The one allowance: on the endpoints that take no credentials (sign-in, setup) a cookie that does not validate is ignored, so a browser with a stale cookie can sign in; a bad bearer token is refused there too. A *partial* session (second factor owed) sets no caller: only `auth/second-factor` and `auth/logout` use it. The channel is `Api`; the client IP is the request's remote address (IPv4-mapped shown as IPv4): on the internal admin listener that is the forwarded client address the proxy resolved; every other listener trusts no forwarded header.
- **CSRF** for unsafe methods on `/api/`: a bearer request is exempt; `Sec-Fetch-Site` if sent must be `same-origin`; otherwise `Origin` must equal the request's own `scheme://host:port`; with neither header (curl) a request is allowed unless it carries the session cookie. A cookie request with a body must be `application/json` (`+json`), or a type its endpoint lists with `AcceptsAdminContentTypes`. Refusals are a 403 problem with `code: csrf.refused`.
- **Setup gate.** While `SetupService.IsCompleteAsync` is false, only `/healthz`, `/readyz`, `/api/v1/setup` and `AdminPipelineHooks.SetupAllowedPathPrefixes` (`/openapi`, `/api/v1/openapi.json`, `/api/docs`; the API branch adds more there) are served; everything else is a 503 problem (`code: setup.required`, pointing at `/api/v1/setup`). The state is read per request, so finishing setup opens the app at once (paths are matched as written: `/api/v1/setup/` with a trailing slash is not the setup endpoint and stays gated); if it cannot be read (config store down) the gate stays shut (`setup.unavailable`). `POST /api/v1/setup` takes the setup token, username and password, creates the Owner, signs them in (cookie set, 201), audits both outcomes; a wrong token is 403, a finished setup 409, a weak password 422.
- **Rate limiting.** `System.Threading.RateLimiting` fixed windows (the library under ASP.NET Core's rate limiter, used directly because the per-username partition needs the parsed body) on login, second factor and setup, independent of the lockout. **Per client** every attempt, successful or not, takes a permit (an IPv6 client is keyed by its /64); **per username** (the second factor: per user) only *failed* attempts count, so the owner's own sign-ins never use the budget. A refusal is 429 with `Retry-After` (the time left in the window) and `code: auth.rateLimited`. Defaults 20 per client and 10 failures per user per minute: `Paduraksa:Admin:RateLimit:{PermitsPerIp (1-10000), PermitsPerUser (1-1000), Window (1 s-10 min)}`. Memory is bounded: at most 10 000 tracked clients and as many usernames; past that, new keys share one overflow bucket, and expired windows are swept (at most once a second). **Password derivation is bounded too**: login, setup, the second factor and every re-authentication (password change, TOTP enrolment and removal, recovery codes) run in one of `Environment.ProcessorCount` slots; an attempt that gets none within 2 s is a 503 (`code: auth.busy`, `Retry-After: 1`) and derives nothing. Windows and slots are in memory. Per-client limits key on the request's remote address, so on the internal admin listener they key on the forwarded client address (and see the warning in §3.1 about proxying to the admin port).
- **Hardening.** Every admin response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` unless the response set its own (or its path is in `AdminPipelineHooks.CspExemptPathPrefixes`), `Cache-Control: no-store` on `/api/`, HSTS (`max-age=31536000`) on HTTPS requests, except for a loopback host name (`localhost`, `127.0.0.1`, `[::1]`), so a browser does not pin it. Request bodies are limited to `Paduraksa:Admin:MaxRequestBodyBytes` (default 64 KiB, 1 KiB-16 MiB; over it is 413); an endpoint raises its own with `.WithAdminBodyLimit(bytes)`. `Paduraksa:Listen:AdminAllowedSources` (addresses or CIDRs; empty means no restriction) is enforced per connection on the main listener, before TLS: the TCP handshake completes and the connection is then aborted unanswered. **Loopback is not implied** once the list is non-empty (list `127.0.0.1/32` or `::1/128` to allow it); IPv4-mapped IPv6 blocks are refused by the validator (clients are matched as IPv4). Bodies of unknown length (chunked, HTTP/2 without Content-Length) are counted as they are read, so the limit holds for them too. DTOs are read strictly through the HTTP JSON options (`IdentityJsonContext.AddTo`: unknown properties, missing members and nulls where not allowed are 400s; typed IDs, role and permission names as in the context). That sets `RespectNullableAnnotations` and `RespectRequiredConstructorParameters` on the admin's HTTP JSON options for every type.
- **Loopback fallback.** `Paduraksa:Listen:AdminLoopbackHttp` (a port, 0 = off, distinct from the other ports) adds a plain-HTTP listener bound by `ListenLocalhost` to 127.0.0.1 and ::1 only; nothing configures another address. Same app and authentication. The cookie is still sent `Secure` (ASP.NET Core does not check the scheme): Chromium and Firefox store and send a `Secure` cookie for `http://localhost` and `http://127.0.0.1`; Safari does not. HSTS is not sent there, and the same-origin check uses the request's own `http` scheme. **DNS rebinding:** on that listener only a `Host` of `localhost`, `127.0.0.1` or `[::1]` with the listener's port is served; any other is a 400 before anything else runs. The allowlist does not apply to it (it is loopback-only by construction).
- **As built (M4): the admin certificate and the root download.** The admin listener serves a leaf the process issues from the local CA and keeps current: the stable `AdminCertificate.Id`, source `local_ca`, label `Admin (internal CA)`, names from `Paduraksa:Admin:CertificateNames` plus localhost, the loopback addresses, the machine's host name and a specific `Paduraksa:Listen:AdminBind`; re-issued only when that set changes or a third or less of its lifetime is left, always under the same ID, and neither deletable nor re-issuable by hand (`certificate.managed`). It is reserved for the admin port - left out of every inventory the compiler sees, and refused as a Specific binding or the default certificate - served through the vault's `IServerCertificateSource` with a per-handshake selection callback (hot-swap, no restart), ensured by a core-host service before the listeners bind (bounded by `Paduraksa:Admin:CertificateStartupTimeout`, with the run serving what the vault holds before it starts the inventory step, and cancelled and awaited on stop) and re-checked daily, registered without republishing the live config, and falling back to the placeholder with an Error log only when the vault has nothing servable, so the admin port is always up and neither a failure nor a rollback discards a certificate the vault holds. A `vault.db` lost under an intact config database is repaired on the next start: the stale root row is retired and a new root and leaf are made. The root is downloadable for trust-once: `GET /api/v1/ca/root.pem`, `GET /api/v1/ca/root.crt` (`application/x-x509-ca-cert`) and `GET /api/v1/ca` (JSON), plus `HEAD`, anonymous and open during setup (the prefix is one of the setup gate's allowed ones), serving the public root only from the in-memory `CaRootSource` (PLAN §3, **As built (M4): the admin certificate**). `Paduraksa:Admin:CertificateNames` is validated at startup (DNS names and IP addresses; no wildcards or IPv6 zone ids; at most 95, so the certificate stays inside the vault's 100 - both numbers come from `CertificateLimits.MaxNames`). The startup log prints the admin URLs and the root fingerprint at Information while setup is incomplete, alongside the setup token's banner.
- **Not built:** passkeys; a login-throttle store that survives a restart (the windows are in memory; the lockout is in the database). The §3.1 internal listener and forwarded-header trust are built (see §3.1, **As built (M4)**).

### 10.2 Proxied-host auth (`AuthProvider` per host/route)
- **Access lists:** IP allow/deny + HTTP basic auth (hashes compiled into the snapshot; PBKDF2 verification cost is cached per credential+IP for a short TTL).
- **Forward-auth** (authentik, Authelia, oauth2-proxy presets): a sub-request to the auth endpoint with the original method/URI/headers. 2xx → copy the configured response headers upstream. 401/302 → relay to the client. A short-TTL decision cache keyed by the session-cookie hash keeps it cheap. This path allocates (an outbound HTTP call), which is accepted and documented.
- **Native OIDC per host** (later): Paduraksa as the relying party with a session cookie on the host's domain.

### 11.1 REST API (`/api/v1`, admin port)
- Minimal APIs, grouped per resource, built-in .NET 10 OpenAPI 3.1 document + Scalar UI at `/api/docs`.
- Conventions: typed-ID path params (`/hosts/{id:HostId}`), `If-Match: <revision>` for concurrency, `?dryRun=true`, `?force=true` for the admin host's lock-out guard (§3.1), RFC 9457 problem details, cursor pagination (UUIDv7/Int64Ordered IDs make cursors trivial).

- **As built (M4): the identity endpoints** (`Paduraksa.Admin/Identity`, all under `/api/v1`, bodies and responses are the `Paduraksa.Contracts.Identity` DTOs; route parameters carry the ID's route constraint (`users/{id:UserId}`, `sessions/{id:SessionId}`, `tokens/{id:ApiTokenId}`), so a malformed, wrong-type or empty ID doesn't match the route and is a 404, and the handler receives the typed ID (the `?userId=` filters parse the same way and name nothing when it doesn't parse)). `GET|POST setup`; `POST auth/login` (200 with `secondFactorRequired`; the cookie is never in a body), `auth/second-factor` (the cookie value rotates), `auth/logout` (204, cookie cleared), `GET auth/me` (user, roles, effective permissions, `authKind` (`AuthKind`, an enum serialized by name: `session`, `token` or `unspecified`)); `POST me/password`, `POST me/totp/enrollment` (needs the password; the otpauth URI once), `POST me/totp/enrollment/confirm` (returns the recovery codes once), `DELETE me/totp` (password in the body), `POST me/recovery-codes`; `GET sessions[?userId]`, `DELETE sessions/{id}`, `POST sessions/revoke-others` (needs a session; a token caller is refused by that requirement first with 403 `auth.sessionRequired`, so there is no 422 branch); `GET tokens[?userId]`, `POST tokens` (201, secret once), `DELETE tokens/{id}`; `GET|POST users`, `GET|PATCH|DELETE users/{id}` (`PATCH` takes `displayName`, `roles`, `disabled`, applied by one `UserService.UpdateAsync` call in one transaction, the last-Owner guard included: it all applies or none of it does). **A token cannot manage tokens or sessions**: every `tokens` and `sessions` endpoint answers a token caller with a 403 (`code: auth.sessionRequired`, "API tokens can't manage tokens or sessions; use a signed-in session"), so a leaked token cannot mint a longer life for itself or end the session that is watching it. **As built (M4, resource API).** `Paduraksa.Admin`: `AddPaduraksaAdminApi` / `MapPaduraksaAdminApi` / `UsePaduraksaAdminApi`, one file per resource group (`Api/*Endpoints.cs`); `AdminApp` only calls them.
- **Pipeline.** `UsePaduraksaAdminApi` is the first middleware, called before `UsePaduraksaAdminAuth` (a call order, asserted by a test in which an exception inside the auth pipeline gets its 500 problem). Endpoints are mapped after the auth pipeline. The security-headers middleware (auth) adds its headers when the response starts, so a failed response, reset by the problem middleware, keeps them; its default CSP is added only when none is set, and the docs page sets its own before the response starts.
- **Errors.** Every error under `/api` is RFC 9457 `application/problem+json`, one shape (`ApiProblem` in Contracts: `type`, `title`, `status`, `detail`, `traceId`, `instance`; `code` for a stable machine name; `errors`/`relatedErrors`/`warnings`/`conflict`/`revision`/`version` when they apply). The auth pipeline's problems (401, 403, 429, 503 setup gate, identity outcomes) are the same shape with a `code`; its former validation `errors` dictionaries are `errors` lists of `{path, code, message}` like every other 422. `ApiPipelineMiddleware` logs an unhandled exception with the trace ID and answers a fixed 500 with the ID and nothing of the exception; gives routing's and binding's empty 404/405/400 a body; a `BadHttpRequestException` keeps its status (413). A `JsonException` is answered with a fixed sentence and the member's path, never its message (which names CLR types); a polymorphic member without its discriminator is a 400.
- **JSON.** Bodies are read and written through `AdminJsonContext` directly: JSON only (415 otherwise), strict. `AdminJsonContext.AddTo(options)` (idempotent) puts the same strictness, the typed-ID converter factory and the enum-name converters on the host's HTTP options (a context in the resolver chain alone brings neither). Core enums use their `ModelNames` names, config enums camelCase. Every DTO a response or request carries reads back what the API writes: a nullable constructor parameter has a default (a test walks the DTO graph and fails for one without), and a unit test writes and strictly reads every DTO through the HTTP options.
- **Typed IDs.** Route constraints per ID type (`/hosts/{id:HostId}`; a malformed or wrong-type ID is a 404); parameters and schemas in the OpenAPI document are the typed-ID string schema (`pattern`, a valid example).
- **Concurrency.** Reads carry `ETag`: an object's version (`"3"`), or the latest revision's ID for `GET /config` and the lists. A change to an existing object needs `If-Match` with one quoted strong tag: missing is **428**, stale or weak **412** (the problem's `conflict` says what is current), an unquoted tag, a list, `*` or a version with a leading zero 400. `POST` creates need none (an existing ID is 409). A route is changed through its host: `If-Match` is the host's version. `POST revisions/{id}/rollback` takes the latest revision's ID. `?dryRun=true` runs the whole command and returns the plan without committing; `?message=` is the revision note. Statuses: committed 200/201 (deletes 204, a PUT that creates a route 201 with `Location`), invalid 422 (the pipeline's errors verbatim), denied 403, store unavailable 503. **A change that was stored but could not go live is a 500 problem with `code: config.publishFailed`**, the stored `revision` and the new `version` (also the `ETag` header): the client knows the change is stored and not live, and repeating the request with the old `If-Match` is a 412, not a duplicate; nothing retries the publish.
- **Pagination.** `?limit=` (1 to 200, default 50) and `?cursor=` (opaque: the last item's typed ID) on revisions and audit, newest first; an invalid cursor is 400. Audit filters: `from` and `to` (strict ISO 8601 with a zone; `from` after `to` is 400), `actor` (system, cli, a user ID or a token ID: what changes made through a token record is the token), `action` (exact or `prefix*`), `target`; a filter over 128 characters is 400.
- **Body limits.** The auth pipeline's: 64 KiB for JSON; `WithAdminBodyLimit` raises it for certificate uploads (1 MiB + framing) and simulate (1 MiB); uploads declare `AcceptsAdminContentTypes("multipart/form-data")` so a cookie-authenticated upload passes CSRF. The CSRF check covers every unsafe method on a cookie-authenticated request whatever its body, and is tested for the multipart upload and the bodyless renew.
- **Secrets.** Uploads are streamed from the multipart request into `ICertificateImport` (parts `password`, `label`, then `file`, a duplicate `password` or `label` is a 400, nothing after the file is read; the password lives in a cleared `char[]`). DNS credentials and EAB keys are stored by the services (`DnsProviderService.CreateWithCredentialAsync`/`RotateCredentialAsync`/`DeleteWithCredentialAsync`, `AcmeAccountService.CreateWithEabAsync`), which authorize and validate before they store anything and delete the secret again when the provider or account isn't created; no response type can carry a secret. "Test credentials" (`DnsProviderService.TestAsync(id, origin)`) needs `providers:write` and is audited (`acme.dns_provider.test`, verdict only). `RevisionQueryService` and `AuditQueryService` (Application) are the public, DTO-only readers over the internal revision store and audit chain.
- **Issuance.** ACME request and renew run under the application's stopping token, not the request's: a client that gives up doesn't cancel an issuance, and the answer is still synchronous when it finishes. A DNS-01 order waits for propagation and can outlast a typical client timeout; `GET /certificates/{id}/order` shows progress.
- **Description.** OpenAPI 3.1 at `/api/v1/openapi.json` (generated once, cached) and Scalar at `/api/docs` (script embedded in the package and served locally; no fonts, telemetry, agent or MCP hook). CSP `default-src 'none'; script-src 'self' 'nonce-...'; style-src 'self' 'unsafe-inline'; ...; connect-src 'self'`; Scalar's bundle contains no `eval` or `new Function` (a test checks), so there is no `'unsafe-eval'`. Both are anonymous (`AllowAnonymousAdmin`). Every operation, the identity ones included, has a summary and either `x-required-permission`, a sign-in requirement or `security: []`; the description names which resources take `If-Match`, the 428/412/400 rules and `config.publishFailed`. Integration tests check that every mapped `/api/*` endpoint carries `RequiredPermissionMetadata`, `AdminAuthenticatedMetadata` (`RequireAuthenticated`) or `AdminAnonymousMetadata`, and a table checks the exact permission of every resource route and method.
- **Tests** use real authentication: users in every role from the identity services, an API token per role (scoped to the role) as the Bearer credential, and real cookie sessions for the CSRF tests.
- **Not done:** `If-None-Match`/304, whole-document replace/import and YAML (M8), access lists/rule sets/error pages (not in the config model yet), metrics (M7), an ID-generation helper (IDs are client-chosen), a hermetic test of the ACME happy path (needs a CA).

### 11.3 Health endpoints
`GET /healthz` (process alive, snapshot loaded) and `GET /readyz` (listeners bound, a snapshot live, not draining; vault unlocked from M3) on the admin port, plus the loopback plain-HTTP fallback listener when enabled. Unauthenticated, no details beyond status. Readiness means "serving traffic", not "the config database is reachable": a degraded start (§6.4) serves the last-known-good config and is still ready, so `/readyz` answers 200 with the body `degraded` instead of `ready`. These are for **external** monitors and orchestrators (Uptime Kuma, Kubernetes probes, Gatus), which can probe them over HTTP without spawning anything. The image's own Docker `HEALTHCHECK` is the exception (§16).

### 11.4 CLI (same binary, `System.CommandLine`)
`paduraksa serve` (default) · `setup-token` · `admin reset-password <user>` · `admin disable-2fa <user>` · `config export|import [--dry-run]` · `vault rotate-kek` · `backup|restore` · `doctor` (ports, permissions, H3/libmsquic, DNS, clock skew; **as built (M5):** `doctor --liveness` only - the admin `/healthz` over loopback, for the container `HEALTHCHECK`) · `migrate`.

### 11.5 YAML import/export
- YamlDotNet with a static (source-generated) context. Format:
  ```yaml
  apiVersion: paduraksa.dev/v1
  kind: Config
  settings: { defaults: {...} }
  profiles: [...]
  upstreams: [...]
  hosts:
    - id: host_0J9zb3xQk1Lr8m2V7aYc4D   # optional on import; matched by id, else by first hostname
      names: [jellyfin.example.com]
      profile: media
      routes: [{ path: /, upstream: jellyfin }]
  certificates: [...]   # metadata + binding only; never key material
  ```
- Import goes through the normal command pipeline (validate → compile → diff → one revision). Modes: `merge` and `replace`.
- The same canonical document is what revisions store, so export = "current revision as YAML".
- The import format above is a friendlier DTO than the document (M8): optional IDs, references by name (`profile: media`, `upstream: jellyfin`), `kind:`. Import maps it onto the strict canonical `ConfigDocument` (§6.4), assigning IDs and resolving names; only that document is stored, and export writes it back in a form that imports to the same document.
- Later: **declarative mode** (§11.6), where a watched file is authoritative and the UI becomes read-only for the objects it manages.

### 11.6 Declarative mode (after v0.1)

For declarative deployments (Kubernetes manifests, Helm, Compose with a mounted file, NixOS, a git repo synced by Flux/Argo or `git-sync`): the desired config lives in files the deployment owns, and Paduraksa converges to them. Not a blocker for v0.1; it builds on the M8 YAML format and import pipeline.

- **Source.** `Paduraksa:Declarative:Path`, a file or a directory of `*.yaml` documents merged in name order (a ConfigMap mount is a directory). Watched with a debounce; Kubernetes updates a mounted ConfigMap by swapping the `..data` symlink, so the watcher follows the directory, not the inode. Also reconciled at startup, before the listeners open, so a pod never serves stale config after a restart.
- **Same pipeline.** A change in the files is one import (§11.5): validate → compile → diff → one revision with channel `declarative`, actor System, and the source file's SHA-256 in the message. An invalid file changes nothing: the last good revision keeps serving, the error is logged and audited, and it shows in the dashboard, in `/readyz` details and in a metric (`paduraksa_declarative_reconcile_ok`). Readiness stays green; a bad commit to the repo must not take the proxy out of rotation.
- **Ownership.** `Mode: Exclusive`: the files are the whole config (import mode `replace`), and the API, MCP and dashboard are read-only for config. `Mode: Managed`: the files manage the objects they name. Those objects are marked `managedBy: declarative` and refused by the other channels with a clear error, while objects the files don't name stay editable. Removing an object from the files deletes it, but only if it is marked managed. The dashboard shows a lock and the source path on managed objects.
- **Secrets stay out of the files.** Credentials are referenced, never inlined: `secretFile: /run/secrets/cloudflare-token` (a mounted Kubernetes Secret or Docker secret). The reconciler streams the file into the vault (`ISecretStore.ReplaceAsync`, keyed by a stable secret ID declared next to it) and re-imports it when it changes. The value never enters the revision document or the audit log. Certificates managed elsewhere (cert-manager, Vault PKI) are referenced the same way (`certFile`/`keyFile` on a `kubernetes.io/tls` Secret mount) and imported through `ICertificateImport`, so the trust boundary (§8) holds. The KEK comes from `PADURAKSA_MASTER_KEY_FILE` on a Secret mount.
- **Identity and setup.** An Owner can be declared, with a password hash or a `passwordFile`, plus roles for other users and API tokens whose secrets come from files. When an Owner is declared, the setup-token gate (§12.1) is skipped. Alternatively `Admin: Disabled` runs the proxy with no admin listener at all, only health and metrics, for fully hands-off clusters.
- **CI support.** `paduraksa config validate <path>` (offline: schema, references, compile; exit code and RFC 9457-style messages) and `paduraksa config diff <path> --against <url|data-dir>` show what a merge would change before it is applied.
- **Kubernetes shape.** Single replica, because SQLite and the vault are single-node: a StatefulSet (or a Deployment with `Recreate`) with a PVC for `/data`, the config as a ConfigMap and the credentials as Secrets. With declarative mode the database becomes mostly a cache of the files plus state (ACME accounts and orders, the vault, audit), so losing the PVC costs reissued certificates, not config. A Helm chart and an example manifest ship with the feature. Multiple replicas are fleet mode (§16.1), where the declarative files feed the control plane.
- **Possible later step.** A Kubernetes **Gateway API / Ingress controller** mode that derives hosts and routes from cluster resources instead of files. It is a different product surface (watching the API server, RBAC, status writes), so it isn't designed here.

### 12.1 First-run wizard
Security: until setup completes, the admin app serves **only** the wizard. That requires a one-time **setup token** printed to the logs and the console (`paduraksa setup-token` reprints it), which stops anyone else on the LAN from claiming the instance.

1. Setup token → 2. **Owner account** (+ optional passkey/TOTP) → 3. **Admin access** (port, bind, allowed CIDRs, admin hostname) → 4. **ACME account** (email, CA, ToS) → 5. **DNS provider** (pick, enter creds → live *Test*) → 6. **Wildcard certificate** (`example.com` + `*.example.com`, with live progress through order → TXT → propagation → issued) → 7. **Global defaults** (security preset: *Off / Balanced / Strict*, HSTS, default-host behaviour, robots preset) → 8. **First host** (optional, with an upstream reachability test) → Done (summary + "export config" + backup reminder).

Each step is skippable where it makes sense (e.g., HTTP-01 only, no DNS provider), and the wizard can be resumed.

**As built (M4).** Setup is incomplete while no Owner exists. At startup (the core host, after the config store) the server writes a 256-bit setup token to `<data dir>/setup-token` (mode 0600; a copy readable by others is discarded and replaced), logs it at Warning as **one boxed banner** (the box sized to its longest line, so the borders always line up; `+`, `-` and `|` when the console's output encoding is not UTF-8) and deletes the file once an Owner exists; `paduraksa setup-token` prints the same banner, or says setup is complete. `SetupService.CompleteSetupAsync(token, username, password, displayName)` compares the token in constant time, then checks that no Owner exists and creates the Owner in one write transaction (two simultaneous attempts make one), audits it, and deletes the token. A wrong token is audited. `SetupService.IsCompleteAsync` is what the admin app asks. CLI: `admin reset-password <user>` reads the password from standard input or a no-echo prompt (never argv), ends the user's sessions and clears a lockout; `admin disable-2fa <user>` turns the second factor off; both are audited as the `cli` actor.

## 16. Deployment

- **Container:** `ghcr.io/<org>/paduraksa:<ver>`, multi-arch (amd64/arm64), Ubuntu Noble base + `libmsquic` (pinned), `ASPNETCORE_HTTP_PORTS` cleared, non-root. Listens on **80/443 (tcp+udp)/9443 inside the container**, mapped 1:1 in compose, so `Alt-Svc` and redirects never see a translated port. Non-root binding below 1024 works because Docker (20.10+) sets `net.ipv4.ip_unprivileged_port_start=0` in the container's network namespace. For `network_mode: host` or other runtimes, the image also gives the apphost `cap_net_bind_service` (`setcap`). The image's own Docker `HEALTHCHECK` uses `paduraksa doctor --liveness` (which calls `/healthz` over loopback) at a 30 s interval, because the image ships no curl/wget. That costs a short-lived process per probe, which is acceptable at that interval. External monitors should hit `/healthz` directly.
- **Bare metal:** self-contained single-file publish + systemd unit (`AmbientCapabilities=CAP_NET_BIND_SERVICE`, `LoadCredential=master.key`).

### 16.1 Fleet mode: control plane and data plane (after v0.1)

**Goal.** Run many proxy replicas (Kubernetes, or several hosts) that share certificates, ACME challenges, config and limits, without giving up what the single node is good at: a hot path with no I/O, keys that never leave a vault, and a proxy that keeps serving when everything behind it is down. Single-node (`--role all`) stays the default and gets none of the extra machinery.

#### Roles
One binary, `paduraksa serve --role all|control|data`.
- **Control plane** (`control`): admin app, REST/MCP/dashboard, config store and revisions, the authoritative vault, ACME orchestration and the renewal scheduler, audit, the rollout controller and fleet statistics. It serves no proxied traffic. One replica on SQLite is enough: data nodes never touch its database, so **Postgres is only needed for a highly available control plane** (phase F4).
- **Data plane** (`data`): the public app and the hot path only. It has no config database, no admin listener and no ACME client. Its state is a local **bundle cache** (an `emptyDir` or a small volume), so it scales horizontally as a plain Deployment.
- `all` is both roles in one process, wired in-process exactly as today (the sync below is the in-process `ConfigChangeFeed`/`SnapshotStore` path), so single-node users never run a sync protocol.

#### Sync: data nodes keep a fast local copy
Data nodes **connect out** to the control plane over one long-lived mTLS HTTP/2 stream (ASP.NET Core gRPC, first-party). Nothing connects into a data node except proxied traffic, so data nodes need no admin port and work behind NAT.
- **What is synced, content-addressed by SHA-256:**
  - **Config:** the canonical revision document (already canonical JSON with a hash, §6.1). Each node **compiles it locally** with the same compiler, so a snapshot is never shipped as an opaque blob and the node's own certificate table and YARP binding are built the normal way.
  - **Certificates and keys:** chains in plain form; private keys only sealed (see the trust boundary below).
  - **Secrets the hot path needs** (PoW and forward-auth HMAC keys, M6 and later): sealed the same way.
  - **Artifacts:** Cloudflare IP ranges, the Geo DB and error pages. Each is fetched or built once at the control plane and distributed.
  - **ACME HTTP-01 tokens:** a priority channel (below).
- **Delta and resume.** A node reports what it holds (the applied revision, certificate versions, artifact hashes); the control plane sends only what is missing. Every message is idempotent, so a reconnect resumes rather than restarts.
- **Applying.** A node verifies hashes, compiles, publishes through its own `SnapshotStore`, then **acks** with the revision it is serving, or with the compile errors it hit. The control plane always knows which revision each node serves.
- **Static stability.** A node that loses the control plane keeps serving its last applied bundle, which survives a restart through the bundle cache (the same idea as the last-known-good file, §6.4). It reports staleness (`paduraksa_fleet_bundle_age_seconds`), and `/readyz` stays ready. Only certificate expiry limits how long a fleet can run headless, and the control plane alerts long before that.

#### Trust boundary across nodes
Keys still never exist in plaintext outside a vault.
- **Enrolment.** At first start a data node's vault generates a node key pair (X25519 or P-256) and joins with a **join token** (`pdk_join_...`, single-use, or reusable with expiry and a node-group scope for autoscaled pods). The control plane's internal CA issues the node's mTLS client certificate. Nodes get a typed ID, `node_` (UuidV7), and a label set.
- **Vault-to-vault transfer.** The control vault re-wraps a certificate's key for each node's public key (ECDH + HKDF + AES-GCM, AAD = node ID, certificate ID, version). Only the node's vault can unwrap it, and it re-seals locally under its own KEK. This is a new vault capability, `IVaultTransfer`, restricted to enrolled node keys, so the key-material ban list still holds everywhere else.
- **Least privilege.** A node receives only the keys of the certificates its node group serves, so a compromised edge node leaks only its own hosts. Removing a node revokes its certificate, stops its stream and rotates nothing else. Nodes not seen for a configurable time are expired automatically (autoscaled pods come and go).

#### ACME in a fleet
- Ordering, renewal and DNS-01 run only at the control plane; with an HA control plane, behind a leader lease (`ILeaderLease`, always "leader" on a single node).
- **HTTP-01 fan-out with acks.** The orchestrator publishes the token on the priority channel and tells the CA to validate **only after every healthy node that serves the name has acked it** (a bounded wait). Nodes that don't ack in time are listed in the order's step log. The CA's validation request can then land on any pod. Withdrawing the token fans out the same way.
- Renewed certificates are synced like any other certificate change. Certificates bypass rollouts (below): a renewal goes everywhere at once.

#### Rollouts: test config changes on part of the fleet
A commit no longer means "every node, now"; it sets a **target revision per node group**.
- **Node groups and labels:** `zone=eu`, `group=edge`, `canary=true`. A group can also **shard hosts**, serving only the hosts assigned to it, for example an EU edge serving EU hosts. That is also what scopes the keys above.
- **Rollout plans.** Each plan is an ordered list of stages, each a selector or a percentage of nodes plus a bake time, for example canary node → 10 % → 50 % → 100 %, with **gates** between stages:
  - **Manual:** "advance".
  - **Automatic (phase F3):** compare the stage's nodes with the rest of the fleet on gate errors, upstream 5xx rate, p99 latency, compile failures and health-check failures. Any node that fails to compile stops the rollout.
- **Outcomes.** A failed gate pauses the rollout, or rolls it back automatically (the target returns to the previous revision) if the plan says so. An operator can also pause, resume, abort or **apply now** for emergencies.
- **Defaults.** No plan means every node gets the revision immediately, which is today's behaviour. Each rollout start, stage advance, pause and rollback is audited.
- **What a rollout changes.** Only *config revisions* are staged. Certificate changes, ACME tokens, secret rotations and artifact updates go fleet-wide immediately, because holding them back would break something, not test it.
- **What users see.** While a rollout runs, different nodes serve different revisions. The dashboard shows the fleet split per revision. The simulator (§7.7) can target "the revision node X is serving", and access-log entries carry the revision that answered them.

#### Statistics: push the cheap things, pull the heavy ones
- **Push.** Each node sends aggregated **deltas** every 10 s on its sync stream: counters and histogram buckets from the fixed-size M7 metric slots, keyed by host/route/upstream ID, plus its upstream-health view. The payload is small, works through NAT, and gives the rollout gates their data even when nobody has the dashboard open. The control plane merges the deltas into the M7 rollups and exposes fleet-level `/metrics`.
- **Backpressure.** While the control plane is unreachable, a node keeps a bounded ring of deltas (for example 15 min). After that it drops the oldest deltas and counts the drops, so a reconnect backfills recent history and the hot path never blocks on statistics.
- **Pull on demand,** over the same stream, for things too heavy or too rare to push: live access-log tail from selected nodes (opened when a dashboard view asks), per-node destination health detail, connection and TLS debug, a node's current snapshot summary.
- **Prometheus-native too.** Each data node keeps its own `/metrics` on an internal port, so a cluster that already scrapes pods can ignore the fleet aggregate.

#### Rate limits across replicas
Local token buckets on each node, with each node's share of a limit (for example the limit divided by the number of healthy nodes in the group) pushed by the control plane as part of the bundle, so the hot path stays I/O-free. This is approximate by design. Exact shared limits are an option for later: local buckets reconciled asynchronously, gossiped between nodes or batched to Valkey/Redis every ~100 ms, so overshoot is bounded by the sync interval. Never a network round trip per request.

#### Upgrades and version skew
- **Upgrade order:** the control plane is upgraded first and serves data nodes of the same and the previous minor version.
- **Protocol and bundle versions:** the protocol is versioned, and bundles carry the document's `apiVersion` and a minimum compiler version. A node that can't compile a revision acks the error and keeps serving the old one, which also stops any rollout.
- **Migrations:** with an HA control plane they become expand/contract and run once, from the leader or a Job.

#### Kubernetes shape
- **Control plane:** a StatefulSet with 1 replica and a PVC (SQLite), and a Service for the admin UI and for the sync endpoint.
- **Data plane:** a Deployment with an HPA. It gets the join token from a Secret, an `emptyDir` bundle cache, a LoadBalancer Service for 80/443 tcp+udp (`externalTrafficPolicy: Local`, or PROXY protocol from the LB), and PodDisruptionBudgets.
- **Packaging:** a Helm chart with both roles, plus the declarative mode (§11.6) feeding the control plane.

#### Phasing
- **F1:** roles, enrolment, config/certificate/artifact sync with static stability, vault-to-vault key transfer, HTTP-01 fan-out with acks, pushed statistics and the fleet view in the dashboard.
- **F2:** node groups and labels, host sharding with scoped keys, rollout plans with manual gates.
- **F3:** automatic gates and auto-rollback.
- **F4:** an HA control plane (Postgres, leader lease, LISTEN/NOTIFY between control replicas) and exact shared rate limits.

#### Seams worth keeping in the single-node code
These are cheap now and expensive later. Fold them into the milestones that touch the code anyway.
1. **Config source.** The public side gets its snapshots through a config-source abstraction (today the in-process `ConfigService` publish), so a remote bundle source can replace it.
2. **Leader lease.** The ACME scheduler and any other singleton job run through `ILeaderLease`.
3. **Challenge publishing** goes through `IAcmeChallengeStore` publish/withdraw (already a seam) and can grow acks.
4. **Int64Ordered node ID.** The layout reserves bits for a node ID before any data exists, because changing it later is a data migration.
5. **Statistics.** M7 metric slots are designed as mergeable deltas (counters and fixed histogram buckets, no per-node-only aggregates).
6. **Database portability.** SQLite-specific behaviour (`BEGIN IMMEDIATE` serialization, `NOCASE`, rowid keys) stays inside Storage/Data behind intent-named helpers, so the control plane could run on Postgres.
