# M1 baseline, 2026-11-07

The micro-benchmarks and the S7 end-to-end baseline (PLAN §13) on the integrated M1 proxy (`main` 640d11f), plus a GC
and tail-latency experiment. The method, setup and caveats are in [`bench/README.md`](../README.md).

It ran in-process with workstation, non-concurrent GC: 58 benchmarks in 7.6 minutes.

one byte per operation. `AllocAssert` in the tests is the exact per-call guarantee. Times come from a ShortRun on a

## End-to-end: Paduraksa vs nginx vs Caddy

The command was `bench/run-baseline.sh`, with the defaults.
- **Runs:** each 10 s. Each proxy got 10 s of H1 and 10 s of H2 warm-up, each scenario 5 s more, and each fixed rate
  5 s at that rate.
- **Concurrency:** 64 in flight (HTTP/2: 16 connections x 4 streams).
- **Errors:** no request failed in any run.
- **Fixed rates:** each point is a **single 10 s run**, so p99 and p99.9 there are anecdotes (see the GC experiment
  for repeated runs).

The 4 CPUs are 2 physical cores with their SMT siblings, so about 3.2 or more busy is close to saturation. On that
basis the proxied scenarios are CPU-bound for all three proxies, and the CPU figures agree with the throughput ratios:
Paduraksa spends 1.5-1.9x nginx's CPU per request and 0.27-0.44x Caddy's.

In the `answered` scenario Paduraksa and nginx keep 2.8-2.9 CPUs busy, not 3.2+. The load generator can do at least
955k req/s, so it isn't the limit. More likely it's how the 64 connections spread over workers and threads. **Treat
0.54x nginx there as approximate.**

| HTTP/2 at 10k / 30k req/s | 5,059 / 5,054 | 7.1 / 21.6 | 9.9 / 22.8 | 1.92 / 1.33 |

- **Bytes per request don't depend on load:** 4.6 KB at 10k, 30k and ~180k req/s.
- **Against S3:**
  - **Proxied, HTTP/1.1 plain:** 4.6 KB here against S3's 2.5-2.9 KB with minimal headers. The integrated pipeline
    adds the connection middleware, the TLS/scheme checks and Paduraksa's forwarding headers.
  - **Browser-like headers:** 6.9 KB.
  - **Answered by the gate:** 0.8 KB, against S3's 0 B for repeated synthetic traffic. This isn't explained yet;

- **GC:** 24-33 ms of GC pause per second at saturation (2.4-3.3 %), with no single pause above 0.6 ms at fixed
  concurrency.
- **Cloudflare headers** cost about +670 B and +2 µs of CPU per request (5,244 against 4,573 B; 20.0 against 18.1 µs),
  for three extra unknown request headers and the resolver.

## GC and tail-latency experiment

**Setup:** Paduraksa only, HTTP/1.1 plain at 30k req/s, 3 x 10 s runs per GC setting in one runner process. oha kept
its per-request SQLite, and `bench/baseline/stalls.py` grouped slow requests (over 3 ms) into stalls: 10 or more slow
requests whose scheduled starts are within 2 ms of each other. The raw data is in
[`2026-11-07-gc/`](2026-11-07-gc/).

| GC setting | p99 median (range) | p99.9 median | gen0 GCs/s | pause ms/s | max pause ms | req over 3 ms | stalls/s | slow req in stalls |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| Default (Server GC, DATAS on) | 2.21 (2.02-3.34) | 9.51 | 17-27 | 16-24 | 1.3-1.6 | 0.4-1.1 % | 0.7-0.9 | 99 % |
| `DOTNET_GCDynamicAdaptationMode=0` | 1.27 (1.08-1.79) | 5.92 | 1.6-1.9 | 2.9-3.1 | 2.0-2.3 | 0.1-0.4 % | 0.6-0.8 | 95-98 % |
| `DOTNET_GCHeapCount=4` | 2.13 (1.69-2.48) | 8.00 | 1.6-2.1 | 3.3-4.1 | 2.2-2.9 | 0.2-0.7 % | 0.9-1.8 | 95-100 % |
| nginx, same load (2 runs) | 1.52 (1.49-1.55) | 3.44 | - | - | - | 0.1 % | 0.4-0.9 | 95-99 % |
| Caddy, same load (2 runs) | 3.25 (3.17-3.32) | 7.35 | - | - | - | 1.4-1.6 % | 13-14 | 75-78 % |

**What the stalls correlate with:**
- **Process-wide.** 95-100 % of Paduraksa's slow requests fall in stalls that hit 20-110 requests at once, across
  connections. Nothing points to one slow connection or request.
- **Not GC frequency.**
  - With DATAS on there are ~20 gen0 GCs per second; with DATAS off or 4 fixed heaps, ~2. Stalls happen 0.6-1.8 times
    per second in all three.
  - The longest GC pause (≤ 2.9 ms) is shorter than a typical stall's worst latency (median 3.5-8 ms, max 10-20 ms).
- **Not the runner's own sampling.** In an A/B run, the per-second `GC.GetTotalAllocatedBytes(precise: true)` gave the
  same stall rate as `precise: false` (0.6-1.2/s in both); that data isn't committed. Neither did the thread-pool
  queue length line up with stall rates.
- **Partly the environment.** nginx at the same load also shows ~0.4-0.9 stalls per second of the same shape. So part
  of the pattern comes from outside the proxy: oha, the upstream on the shared E-cores, or the host.
  - **Paduraksa's share:** its stalls hold 3-10x more slow requests than nginx's, so stalls hurt it more. Caddy's
    pattern is different: frequent small stalls.
- **No GC setting is clearly better.**
  - DATAS off gave the best p99 here, but before integration the same experiment ranked it worst (p99 5.6 ms against
    3.4 ms for the default). Run-to-run spread is as large as the differences.
  - **Recommendation:** keep the defaults. Attributing the stalls needs a trace (`dotnet-trace` with GC, thread-pool
    and CPU sampling, or `perf sched` for scheduling delay), not per-second counters.

## Summary

- **Where Paduraksa stands.**
  - **Throughput:** 0.57-0.71x nginx's on proxied traffic, and ~0.54x when the proxy answers itself (approximate, see
    above). It is 2.1-3.6x Caddy's.
  - **CPU per request:** 1.5-1.9x nginx's. The same two P-cores and the same upstream are used throughout.
- **Tails.** At fixed rates the median latency is within 0.15 ms of nginx's, but the p99 is 1.4-2.3x nginx's and
  p99.9 is worse.
  The cause is process-wide stalls, which the experiment couldn't pin on GC.
- **Allocations.** About 4.6 KB per proxied request for the whole process (6.9 KB with browser-like headers), and 0 B
  in Paduraksa's own hot path per the micro-benchmarks and tests. The next target is the Kestrel/YARP share
  (PLAN §7.1).
- **Not covered yet:** HTTP/3 (off in every run) and Cloudflare proxy mode. The `cf` scenario uses Tunnel mode, which
  takes the same resolver path.
